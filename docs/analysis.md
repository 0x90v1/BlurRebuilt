## 2. Engine facts that constrain the port

### File system and paks
- Single global `Sys::I_FileSystem*`; in game it is `LogicalFs::C_OverlayFs`. Layers: 0 = loose cwd ("CFileSystem"), then paks mounted by `C_GameSystems::CreateFsLayers` (`amax/game/GameSystems.cpp` 201-265, `USE_NEW_PAK_LAYOUT`). Layer types `E_Type_Overlay` (first hit top-down), `E_Type_Opaque`, `E_Type_Newer`. In non-gold builds `Util.LogicalFs.OverlayFs.MasterDiscEmulation=false` makes every layer Newer, so a newer loose file overrides a pak copy.
- Choke point: `C_OverlayFs::GetBestLayer()` (`util/logicalFs/overlayfs/OverlayFs.cpp` ~488/571). Also `InsertLayer`/`AddLayer` for a new top layer. `Util.LogicalFs.OverlayFs.FileMappingDebug` logs every path-to-layer mapping.
- PC mounts: `cache/root.pak` at `/`, `cache/models.pak` at `/models/`, `cache/shaders-speed.pak` at `/graphics/shaders/speed/`, `cache/gamedata.pak` at `/gamedata/` (RSA-1024 signature `gamedata.sig`, key `g_amax_publicKey`, SHA-1 per file). Not mounted on PC: `root_streaming.pak`, `boot.pak`, `boot_rampak.pak`, `gamedata_boot.pak` (all inside `#ifndef PLATFORM_PC` in `BootLayer.cpp`). `lut_rampak.pak` is gated only by `g_enableLutRamPak`.
- Pak format (`util/logicalFs/pakfs/impl`): `PAK2` fourCC + version + sector size; `C_PakHeader` (SHA-1, codec, fat entry type, separator, meta string offset); XOR-obfuscated string table (key in `PakUtil.cpp`); FAT of `C_PakFatEntry` (32 bytes) or `C_PakFatEntrySecure` (+SHA-1), sorted by CRC. Codecs: Raw, ZLib, XMem, PacketZLib, PacketXMem. Hash: `C_PakCrc32`, poly 0xEDB88320, init 0xFFFFFFFF, no final XOR, over the normalised lowercase path with leading separator. Matches Blur2Test's `~crc32("\\" + path.lower())` on 29,913 of 29,913 records.
- I/O: PC `IoDevice.cpp` uses `CreateFile` with `FILE_FLAG_NO_BUFFERING` (sector-aligned reads). `C_LogFs` wrapper logs every access to `./user/logfs` in non-gold builds.
- **Pak version 2** (T005, 2026-09-23). The source reads version 1 only (`PAK_VERSION 1`); retail PC ships v2 for every pak except `shaders-speed.pak` (v1); Nov discs use v2 for `gamedata.pak` and v3 for `root.pak`. v2 layout, verified on all 7 retail PC paks: pre-header `PAK2`/version/sectorSize as v1; then U32 headerSize = 0x20 and a **packed** 32-byte header `{codec, fatEntryType, separator, unused, U32 codecFlags, U32 metaStrOffset, U64 fileTime, U32 stringTableBlockSize, U32 fatBlockSize, U32 unknown}` (no 20-byte integrity hash; the last word holds leftover characters such as `bin`, `ss`, meaning unknown). String table (U32 size + XOR-crypted names, padded to a sector) starts at **sector 1**, the FAT (U32 count + U32 bytes + entries) right after it, both block sizes sector-aligned as the header says. FAT entries are 40 bytes: the v1 32 bytes (crc, string offset, parent FAT offset in on-disk strides, logical length, U64 file time, U64 start sector) plus `U32 unknown` (per file; not the path CRC, not SHA-1 of stored or logical bytes) and `U32 storedSize`; secure entries append U32 padding + SHA-1 (64 bytes). Payloads have **no stored-size prefix** (v1 had one, not counting itself): ZLib streams start at the sector, PacketZLib starts with the U32 chunk cap 0x10000 then `[U32 size][data]` chunks, Raw is the bytes. The secure SHA-1 is over exactly `storedSize` bytes from the payload start. Retail codecs: root/boot/lut_rampak = PacketZLib (4), gamedata/gamedata_boot = ZLib (2) secure, root_streaming = Raw (1). The retail `gamedata.sig` verifies against the source's `g_amax_publicKey` when the SHA-1 is taken over the raw on-disk FAT bytes. The engine reader now handles v2 (`PAK_VERSION_READ_MAX 2`, `PakRead.cpp` `ReadFatV2`, codecs take the known stored size via `I_PakCompress::SetKnownPhysicalLength`); v3 is not implemented (not needed: Nov paks are extracted by Blur2Test).
- **Retail Xbox 360 Blur 1 paks (2026-09-24, hexdump of the disc under `C:\AIProjects\Blur\GameData\Xbox 360\`).** `cache/root.pak`: `PAK2` magic in big-endian byte order (bytes `50 41 4b 32`; the PC files read `32 4b 41 50`), version 1, sector size 0x800, then a U32 0x28 and the v1 `C_PakHeader` (20-byte SHA-1, codec 5 = `E_Codec_PacketXMem`, fat entry type 0, separator `\`). `shaders-speed.pak` is the same with codec 3 = `E_Codec_XMem`. So the retail 360 disc is pak v1, the version this snapshot reads natively, and the only two obstacles to reading it on PC are byte order (the reader copies structs in host order) and the XMem codecs: `misc_shared/Compression/XMemCompress.cpp` and `pakfs/impl/PakCompress*XMem.cpp` call the XDK `XMem*` API, which has no PC implementation in the tree, so a PC LZX decoder is needed (Blur2Test uses QuickBMS for this). The disc root also carries `default.xex`, `levels/` (showroom, spa_barcelona_oval, uk_brighton, usa_amboy, usa_la_downtown, usa_la_longbeachdocks, usa_la_river), `boot.pak`, `boot_rampak.pak`, `gamedata_boot.pak`, `lut_rampak.pak`, `root_streaming.pak`. Detection of all this is `GameSource::Detect` in `Blur1Multi/code/mercury/library/util/gamesource/`.
- **XMem LZX on PC (T071, 2026-09-24).** Blur1Multi reads Xbox 360 paks through the engine's own pak code with a PC implementation of the XDK xcompress API (`Blur1Multi/code/vendor/xmem-pc`, over libmspack 1.11 `lzxd.c`, LGPL 2.1). Facts established on the way, each checked against Blur2Test's QuickBMS extraction:
  - *Pak reader.* `PakRead.cpp` already byte-swaps big-endian paks (pre-header, `C_PakHeader`, FAT via `BinaryDeserialiserAutoEndian`); the only missing pieces on PC were the XMem codecs. `PakEntryFile.cpp` selects `C_PakCompressXMem`/`C_PakCompressPacketXMem` only under `PLATFORM_XENON || CFG_CONVERTER`, and `misc_shared` compiles `Compression::XMemDecompress` only with `USE_XMEM_COMPRESSION`, which its jamfile defines for Xenon and for PC tool builds, where it links the XDK's Win32 `Xcompress.lib`.
  - *Frame chain.* An XMem LZX stream is a chain of frames `[u16 BE compressed][data]` (32 KB out) or `[FF][u16 BE out][u16 BE compressed][data]`; a zero compressed size ends it (the stream writer emits five zero bytes). The LZX state carries across frames; each frame's data starts a fresh bit reader. Window 128 KB (17 bits) and no reset interval decode everything on both discs. The E8 header bit is read once per stream.
  - *No pad byte after an odd-sized uncompressed block.* CAB-style LZX (libmspack's default) skips one byte after an uncompressed block of odd length; XMem does not: the next block header starts on the byte right after the data. Found on `models/vehicles/foose_stallion_stock.model` (Aug 31 `models.pak`: uncompressed block of 66,791 bytes, next frame 6,903 + 16 + 25,865 = 32,784 compressed bytes). `lzxd.c` has this under `BLUR_XMEM_LZX`.
  - *Packet codec (5).* `[u32 stored][u32 packet 0x10000][chunks]`, chunk `[u32 compressed][XMem frame chain]`, `0xFFFFFFFF` = stored raw. A logical size that is an exact multiple of 64 KB is followed by an empty chunk (`compressed` = 0) that the writer flushed.
  - *Secure paks.* `gamedata.pak`/`gamedata_boot.pak` on the retail 360 and Aug 31 discs are signed with the same `g_amax_publicKey` as retail PC (RSA-1024, PSS, SHA-1, salt 8, libtomcrypt `rsa_verify_hash`); the signature covers the SHA-1 of the FAT **as stored on disk** (big-endian), which was the Xenon build's host order. The PC reader hashed its byte-swapped copy, so the check failed ("Hash doesn't match", fatal only in `CFG_GOLD`); the Blur1Multi overlay of `PakRead.cpp` keeps the on-disk FAT for the hash. Checked with `Blur1Multi/code/tools/xmem-verify/sigcheck.py` (4 of 4 signatures verify over the on-disk FAT, 0 of 4 over the swapped one).
  - *Mount set.* For an Xbox 360 source, `CreateFsLayers` (Blur1Multi overlay) mounts the Xenon list: `root.pak` and `root_streaming.pak` at `/` (the latter with the 128 KB XMA buffer), `shaders-speed.pak` at `/graphics/shaders/speed/`, secure `gamedata.pak` at `/gamedata/`, then `gamedata_boot.pak` as a RAM pak at `/`. `boot.pak`, `boot_rampak.pak` and `lut_rampak.pak` are mounted later by `C_BootLayer` under `#ifndef PLATFORM_PC` (T072 needs them). There is no `models.pak` on the retail 360 disc (models are in `root.pak`); the Aug 31 disc has one, which the Xenon list never mounts.
  - *Disc root marker.* The prototypes' title executable is not `default.xex` (Aug 31: `Kanzen_Speed.xex`); `GameSource::Detect` accepts any `.xex`.
  - *Verified.* Standalone (`Blur1Multi/code/tools/xmem-verify/xmem_verify.cpp`): all 10 Aug 31 archives, 8,385 files, byte-identical to Blur2Test's full extraction, XMem stream files also through `XMemDecompressStream` in 777-byte pieces; all 8 retail 360 archives, 5,842 files, decode to their FAT lengths, and the 49 with a Blur2Test reference are identical. In engine (`BLUR1MULTI_PAKDUMP`, `pakdump_compare.py`): 1,661 files (723 MB) read through the mounted Aug 31 paks and 49 through the retail disc, all identical, no signature errors.
- **The PC code paths in this snapshot were not the shipping ones.** Retail Blur PC (paks dated 2010-04-30) already used pak v2 while this 2010-06-29 tree reads v1, so the Kanzen branch forked before the PC release work landed. Symptoms fixed so far, all `[Blur2PC]`: audio renderer copied the never-allocated 5-channel surround buffer (`renderer.cpp`); `C_GameWorld::ViewDependentFXUpdate` dereferenced the global colour/depth buffers which are only set under `USE_DISPLAY_WINDOWS` (Xenon/PS3) or after `C_ApplicationPC`'s device-reset path succeeds; `C_DamageLayer` never set `m_pDamageVolume` on PC; `C_GameInputManager::GetGameInput` had no bounds check while the UI scripts address pads 0..3 and PC allocates 1 user; a movie renderer whose Bink open failed made `CreateRenderersVolatile` fail and with it the global buffers. Retail `models.pak` does not exist (models are inside `root.pak`); `boot.pak`, `gamedata_boot.pak`, `lut_rampak.pak`, `root_streaming.pak` are not mounted by this source on PC (`.baf` audio banks live in `root_streaming.pak`, hence "Failed to load bank menumusic.baf").
- **PC render path gaps (black frame, fixed 2026-09-23).** Three independent causes, found with an apitrace D3D9 trace (`C:\Tools\apitrace\apitrace-14.0-win32`; `apitrace trace --api d3d9`, then `d3dretrace -s <dir> -S <calls>` snapshots the bound render target at any call): (1) `C_ApplicationBase::RenderSplitscreenViewWithAA` never re-bound the back buffer on PC (Xenon/PS3 do it through `USE_DISPLAY_WINDOWS` `SetWindow`), so the main view drew into whatever target the pre-render passes left bound (a 512x256 downsample) and the post-process then copied an empty back buffer; (2) `C_HighDynamicRange::CreateLookupTexture` loads the colour-grading LUT with `E_Usage_System` because on PS3 (`TONEMAP_COMBINE`) it is only read by the CPU; on PC it is bound to sampler 8 directly and a system-memory texture samples as black, so the tone-map output was black; (3) movie renderer failure blocked the global colour/depth buffers (see above). The in-game "inf FPS" overlay is `GameDebug::C_MiniPerfMonitor` (on by default outside Master, `GameSys.MiniMonitor.Enable`). It does not read the Mercury profiler: it reads `CPU_TIMING`/`GPU_TIMING` stats named `CPU`, `CPU.Update`, `CPU.Render`, `CPU.Present`, `CPU.Update.Physics`, `GPU`, `GPU.Present`, and only `Application360.cpp`/`ApplicationPS3.cpp` open the frame-level ones and call `C_CPUTimingStats::UpdateStats`; the PC `IdleLoop` did neither, so CPU total was 0 and FPS = 999/0. `C_GPUTimingStats` has Xenon and PS3 backends only. Fixed 2026-09-24 (T063): the PC loop opens the same scopes, and a PC backend in `GPUTiming.cpp` times GPU events with D3D9 timestamp query pairs read 3 frames later (released in `DestroyD3D9`). Neither exists in retail (Master, `CFG_GOLD`, compiles both timing systems out). With decoupled update the Update and Physics rows are non-zero only on frames that ran an update; FPS counts the whole loop including the optional `BLUR2PC_FRAMELIMIT` wait. The profiler bar display (`System.Performance.ShowStats`, `C_DebugHUDPerf`) still needs `ENABLE_MERCURY_PROFILER` (Debug/RelWithDebInfo builds).
- **Built-in shaders need `/Zpr`.** The engine uploads matrices row by row; Bizarre's PC shader scripts compile with `/Zpr` (`mercury/applications/Graphics/TestDisplay/src/mk_common_pc_mesh.bat`). Without it every built-in UI/decal shader got its matrices transposed and drew nothing (invisible UI). `shadergen.py` now passes `/Zpr`.
- **Frame rate: 60 Hz simulation, uncapped interpolated rendering (2026-09-24).** The timer floor was 1/60 s, so above 60 fps the game ran fps/60 times fast; the floor is now 1 ms. The simulation cannot take shorter steps: `RacingPhysics::Car` integrates a hard-coded 1/60 s per step (`car.cpp`, `CreateGravityCache` sets `m_dd.frameTime = 1/60`), and much per-frame game logic (vehicle `FakePhysics` forces added per frame, pickup/decoy/reverse-nitro rotations, input auto-repeat, light trails) assumed one frame per step, as the Aib0t write-up found. So the PC loop (`C_Application::IdleLoop`, ApplicationPC.cpp) now decouples update from render: the game update runs only when 1/60 s of real time has accrued, consuming whole ticks (max 4) and reporting exactly that time to the game through the timer's forced frame time (`g_Blur2PCForcedFrameTime`), so every update runs whole 60 Hz steps; every loop iteration renders. Rendered frames between updates blend poses: `WorldRender::C_ModelInstance::SetElementMatrix` records each element matrix's previous-tick and current-tick values; before a render the ones that moved on the latest tick are written as a blend (quaternion slerp, linear position and scale; jumps over 20 m are not blended) and restored after it. The camera uses its existing motion-blur interpolation (`C_Camera` previous pose, `I_Feed::ToViewSetup`) shifted by the render fraction, only for cameras updated on the latest tick. Cost: up to one tick (16.7 ms) of display latency. Measured: 144 fps render, 60 Hz update, camera advancing 0.33 m on every rendered frame at speed (previously repeated positions). `BLUR2PC_DECOUPLE=0` restores one update per rendered frame; `Framework.Timer.FrameLimit` / `BLUR2PC_FRAMELIMIT` caps rendered fps (default 0, uncapped). Car blob shadows are interpolated too: `C_DynamicBlobShadowInstance::UpdatePosition` keeps the previous and latest caster pose and ground point, and `C_BlobShadows::PreRender` blends them with the same fraction (`WorldRender::Blur2PCInterpRenderAlpha`). Not interpolated yet: particles, headlight projections and HUD markers stay at the latest tick, so they can lead a moving car by up to one tick. **Body/wheel jitter (fixed 2026-09-24):** vehicle parts store their world matrices through `C_Part::m_pWorldMatrix` (Component.cpp), bypassing `SetElementMatrix`, so only the wheels were blended and the body sat one tick ahead; the interpolation registry is now keyed by destination matrix address (`Blur2PCInterpRecordStore`) and the part store path records too. **Body-vs-parts jitter and photo-mode camera swings (fixed 2026-09-24, later):** two more paths bypassed the blend. (1) `C_VehicleActor::DeferredUpdate` writes the body's element matrices (every non-wheel element, `m_WorldMatrices`, VehicleActor.cpp ~750) straight into material data, so the body drew at the latest tick while doors, bumpers and wheels drew blended; those stores are recorded now (`m_Blur2PCWorldMatrixOwners` keeps the owning model instance per pointer). (2) The camera blend used `C_Camera::m_PrevPosition`, which is a motion-blur input in this engine: `C_VehicleFeed::SetMotionBlur`, `C_AmaxChaseCamera::SetMotionBlur` and `C_CameraSystem::Update` (photo camera: `Position() - MotionBlur()`) overwrite it every update with an artificial blur vector, so in photo mode the view swung along the user's blur setting every frame. `C_Camera::GetPrevPosition` now also captures the real previous-update pose (`m_Blur2PCPrevPosition/Shaken/Fov`), and `I_Feed::ToViewSetup` computes the motion-blur matrices exactly as before and then shifts them by the delta from the latest pose to the render-fraction pose on that real line, so the blur inputs are untouched. **AI rims, animated meshes (fixed 2026-09-24, later still):** `C_VehicleActor::SynchData` stores the tyre, alloy rim, brake disc and brake caliper matrices raw through the part's world-matrix pointer (VehicleActor.cpp ~5064-5084); recorded now. Animated models (`AnimatedModel::C_AnimatedModelInstance::Update` and `SetJointTransformParameters`: drivers, animated special-effect meshes such as the vehicle-attached pickup effects, animated level objects) write element and skinning matrices raw, and they do it from update tasks that `C_GameWorld::BeginFrame` flushes inside the render (`C_ApplicationBase::CommonRender`), after the blend pass. The registry gained `Blur2PCInterpRecordTickStore`/`...43` for stores that belong to the current tick even when issued inside a render: the value is recorded and the blend written immediately, then restored after the render like the rest; skinning palettes (`MathsStorage::MatrixRow43`, three float4 columns) are supported as a second destination layout. Plain stores inside a render (`C_ModelSingleElementRender::UpdateElementMatrix` and similar render-time writers) keep the old rule and are left alone. - **Single-instance guard (fixed 2026-09-24).** Without one, launching a second `Amax.exe` starts to a black screen instead of failing cleanly (two processes fight over the same D3D9 adapter/window). Read retail Blur.exe 1.2 with Ghidra (`code/tools/ghidra_retail`) to find its mechanism: very early in `WinMain` it calls `OpenMutexA(MUTEX_ALL_ACCESS, FALSE, "BlurMutex")`; the collision branch (`FUN_01efe771`, reached by a manually-pushed return address into a JMP-through-IAT tail call, not a plain `CALL`) hands off into a runtime bytecode interpreter (`FUN_01fc9113`: `cpuid`, an interlocked spin-wait, a rotate-decode loop, then an indirect call to a computed address) — the signature of a commercial DRM/anti-piracy wrapper (SecuROM-style), not Bizarre Creations' own source, and not something to reverse-engineer or reproduce. ### Resources and chunk files
- `Resource::C_Manager` keyed by normalised filename; `C_LoadingThread`; states Constructed → InLoadQueue → Loading → PostLoading → Ready → Evicting → Deleted; eviction delay.
- All chunk files: platform FourCC first (`Platform.h`: `PC  `, `360 `, `PS3 `), then `Sys::C_FileBlock` chunks with `C_BlockHeader` {8-byte id, U32 size, U16 count}. `GameResource::ValidatePlatformId` fails hard on a mismatch; a missing FourCC only warns. All reads are `NoEndianSwap`.
- Version constants: level `E_SceneFileVersion_Current`=0; physics 0; levelrender `E_LevelRenderFileVersion_Current`=1 (EffectVariation); model 0; model render 0; `E_ModelDataFileVersion` 0/1; texture 0; light list 1; Gravity physics 10; XT flask 1-2; `SERIALISATION_VERSION`: Target::Scene 1, StreamData 3, ChunkInfo 1, SamplerState 1, Primitive 1, PvsCellData 1, others 0. Only the Arch archive (`binaryarchive.h:285`, debug) and LightList reject newer data; everything else branches on `>=`.

### Level pipeline
- `C_LevelState::Finished` (`GameLogic/Structures/LevelState.cpp` 280-300): `.\levels\%s\level.level`, `.\gamedata\levels\%s`, `.\gamedata\levels\%s\%s.aid`.
- `C_AmaxWorldLayer::Create` (`GameLogic/Layers/AmaxWorldLayer.cpp` 545): level handle load → AI data → `InstantiateLevel` (route mask `1 << routeNumber`) → `LoadActorStudioActors` (`actorpack.xt` via `XtPackOpen`).
- `C_LevelResource` (`gamesys/game_resource/source/LevelResource.cpp`): `.level` = Level{Header, MdlDat, NavDat, Advert, MtaDbg}; `.levelphysics` = `C_PhysicsLevel::Load` Physic{Header, Main, per-route}; `.levelrender` = `WorldRender::C_RenderLevel::Read` Render{Header, Scene, Lights, LS, PVSData, CubePt2, Portals, Crowd}; `.levelstream` = `StreamData::OpenStreamFile`, `StreamManager` loader thread does SetPosition+Read per chunk throttled by `g_maxMbPerSecond`, decompressed by scheduler jobs.
- No `.levelanim` loader exists. Level animation in this source is XT-driven (`shared_actors/source/XtLevelAnimation.cpp`).
- Geometry/textures baked into render+stream, referenced by `ResourceIndex{block,index}` (block -1 = shared). Shared textures by name + U32 hash (`SharedTextureManager::InsertTexture`). Props/vehicles by path string via XT `GameModel.Filename`.

### Shaders
- `FX::GetShaderPath()` = `graphics\shaders\speed\`; `FX::Manager::LoadEffectInternal` opens `.fxb`; `ImportFXB` (`FXB.cpp`) finds the `PCFX` block; `Shaders.cpp` calls `CreatePixelShader`/`CreateVertexShader` on embedded D3D9 bytecode. Built-in display shaders are compiled into the exe (`REF_SHADER`). D3DX compilation only in the offline `Fx_export.cpp`. `graphics.fx.ReloadableFx` enables hot reload. No on-disk shader cache exists.
- Discs: `shaders-speed.pak` / `shaders-debug.pak` hold FXB2 containers with XEFX v9 (Aug 31) or v12 (Nov) technique graphs and Xenos microcode + D3DX constant tables. No HLSL source. Engine shaders (sky, tonemap, compositor) live inside the XEX. Blur2Test recompiles microcode with XenosRecomp (`_work\XenosRecomp`) and already emits 152 URP shaders. 92 of 94 stage-referenced shaders exist on the discs (`BillBoard_VTX_LN`, `default_NB_NM_NV` missing).

### Timing (frame-rate coupling)
Confirmed against https://github.com/Aib0t/write-ups/blob/main/blur-fps-unlock/readme.md:
- `C_GameWorld::CalcNumberOfSteps` (`GameWorld.cpp` 2438): `m_GameStep = (S32)(m_GameFraction * 60 + 0.5)`; 50 Hz variant behind `TimeStep50Hz`. Step loop at 2543 clamps at `Game.MaxPhysicsUpdates` (2 or 4 depending on config) so under 30 fps the simulation slows. Clamp inside the accumulator is commented out (network timers).
- Frame-counted consumers: `C_GameInput::GetButtonAutoRepeat` now counts real held time in 1/60 s ticks on PC. The rest (`Perks.PickupActor.RotationSpeed`, `Perks.NitrousReverse.RotationSpeed`, decoy rotation, vehicle fake-physics forces, camera update message `min(steps, max)/60`) see exactly one 60 Hz step per update under the decoupled loop, which is the retail PC behaviour, so they need no change.
