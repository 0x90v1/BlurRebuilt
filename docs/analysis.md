### Build description extracted from the jamfiles (T002, 2026-09-23)
- Tool: `code/tools/jam2cmake/jamextract.py`, a Python interpreter for the Jam subset the jamfiles use plus Bizarre's custom rules. Run from the repo root: `python code/tools/jam2cmake/jamextract.py --top . --root code/amax/game/jamfile.jam --target WIN32 --platform PC --build Speed --out _work/build/targets_pc_speed.json` (and `--build Debug`). Output: one JSON with every target (kind, dir, sources, PCH source, PCH headers, include dirs with existence flags, defines), per-file `object_defines`, `cpfiles`/`importcp` (shader-constant header generation), the Lua bundle list (137 scripts), final `LINKLIBS`/`LINKFLAGS`, and diagnostics.

Per-file: `SPU_NET_TASK` on RacingPhysics `car.cpp`/`networkupdate.cpp`; `DEFLATE_MODULE`/`INFLATE_MODULE` on `PakCompressPacketZLib.cpp` (on PC the file is compiled once, plain).
- Link inputs on PC: `secur32 crypt32 ws2_32 dbghelp psapi`, DirectX SDK `dxerr d3d9 d3dx9 dinput8 dxguid xinput`, OpenAL 1.1 `OpenAL32`+`EFX-Util`, Demonware 2.0 (`bdConnection bdCore bdLobby bdSocket bdPlatform bdNet bdExampleCommonLobby ssleay32 libeay32 libcurl`, present in tree), Bink `binkw32`, Massive `xmassiveadclientlogging`. Flags `/SUBSYSTEM:WINDOWS /MACHINE:X86 /DEBUG /NODEFAULTLIB:LIBCMTD /NODEFAULTLIB:LIBCMT` (so the CRT is the DLL runtime). x86 only.
- Gaps the JSON reports: one stale PCH reference (`amax/library/Kanzen/jamfile.jam` names `StdAfx.cpp`; the files are `Kanzen_PCH.cpp/.h`); 18 missing include dirs, all explainable: `Amax$(_PLATFORM)` (empty on PC), `Code/Genesis/Library/include` (dead), `Advertising/IncludePath` (jamfile typo), `common/ai/air/include` (wrong path in one jamfile), and the vendor dirs Bink, Massive, OpenAL, `libs/vendor/jpeg/version62` (IJG libjpeg 6b, needed by `JpegHelper`). Library `Jpeg` is linked but has no jamfile in the tree.
- Generated headers: `CPFile x.cp|.cv|.sp` produces `x.h` next to the source with `#define CP_NAME n` + `#define CCP_NAME cn` (`.cp`, pixel constants), `CV_`/`CCV_` (`.cv`, vertex constants), `SP_`/`SSP_` (`.sp`, samplers; used as `register(SSP_...)`). Directives: `#set N` (counter), `#begin N` … `#end`, `#align N`, `#include "other.cp"` (chains parent module constants), `#skip`. `ImportCP header : TOP … Module` copies a generated header from another module into the current one. A reference output exists at `code/tools/spt_billboard/source/spt_billboard/shaders/{ps,vs}Constants.h`. 12 CPFile and 26 ImportCP records are in the JSON; the generator is T003 work.

## 2. Engine facts that constrain the port

### File system and paks
- Single global `Sys::I_FileSystem*`; in game it is `LogicalFs::C_OverlayFs`. Layers: 0 = loose cwd ("CFileSystem"), then paks mounted by `C_GameSystems::CreateFsLayers` (`amax/game/GameSystems.cpp` 201-265, `USE_NEW_PAK_LAYOUT`). Layer types `E_Type_Overlay` (first hit top-down), `E_Type_Opaque`, `E_Type_Newer`. In non-gold builds `Util.LogicalFs.OverlayFs.MasterDiscEmulation=false` makes every layer Newer, so a newer loose file overrides a pak copy.
- Choke point: `C_OverlayFs::GetBestLayer()` (`util/logicalFs/overlayfs/OverlayFs.cpp` ~488/571). Also `InsertLayer`/`AddLayer` for a new top layer. `Util.LogicalFs.OverlayFs.FileMappingDebug` logs every path-to-layer mapping.
- PC mounts: `cache/root.pak` at `/`, `cache/models.pak` at `/models/`, `cache/shaders-speed.pak` at `/graphics/shaders/speed/`, `cache/gamedata.pak` at `/gamedata/` (RSA-1024 signature `gamedata.sig`, key `g_amax_publicKey`, SHA-1 per file). Not mounted on PC: `root_streaming.pak`, `boot.pak`, `boot_rampak.pak`, `gamedata_boot.pak` (all inside `#ifndef PLATFORM_PC` in `BootLayer.cpp`). `lut_rampak.pak` is gated only by `g_enableLutRamPak`.
- Pak format (`util/logicalFs/pakfs/impl`): `PAK2` fourCC + version + sector size; `C_PakHeader` (SHA-1, codec, fat entry type, separator, meta string offset); XOR-obfuscated string table (key in `PakUtil.cpp`); FAT of `C_PakFatEntry` (32 bytes) or `C_PakFatEntrySecure` (+SHA-1), sorted by CRC. Codecs: Raw, ZLib, XMem, PacketZLib, PacketXMem. Hash: `C_PakCrc32`, poly 0xEDB88320, init 0xFFFFFFFF, no final XOR, over the normalised lowercase path with leading separator.
- I/O: PC `IoDevice.cpp` uses `CreateFile` with `FILE_FLAG_NO_BUFFERING` (sector-aligned reads). `C_LogFs` wrapper logs every access to `./user/logfs` in non-gold builds.
- **Pak version 2** (T005, 2026-09-23). The source reads version 1 only (`PAK_VERSION 1`); retail PC ships v2 for every pak except `shaders-speed.pak` (v1). v2 layout, verified on all 7 retail PC paks: pre-header `PAK2`/version/sectorSize as v1; then U32 headerSize = 0x20 and a **packed** 32-byte header `{codec, fatEntryType, separator, unused, U32 codecFlags, U32 metaStrOffset, U64 fileTime, U32 stringTableBlockSize, U32 fatBlockSize, U32 unknown}` (no 20-byte integrity hash; the last word holds leftover characters such as `bin`, `ss`, meaning unknown). String table (U32 size + XOR-crypted names, padded to a sector) starts at **sector 1**, the FAT (U32 count + U32 bytes + entries) right after it, both block sizes sector-aligned as the header says. FAT entries are 40 bytes: the v1 32 bytes (crc, string offset, parent FAT offset in on-disk strides, logical length, U64 file time, U64 start sector) plus `U32 unknown` (per file; not the path CRC, not SHA-1 of stored or logical bytes) and `U32 storedSize`; secure entries append U32 padding + SHA-1 (64 bytes). Payloads have **no stored-size prefix** (v1 had one, not counting itself): ZLib streams start at the sector, PacketZLib starts with the U32 chunk cap 0x10000 then `[U32 size][data]` chunks, Raw is the bytes. The secure SHA-1 is over exactly `storedSize` bytes from the payload start. Retail codecs: root/boot/lut_rampak = PacketZLib (4), gamedata/gamedata_boot = ZLib (2) secure, root_streaming = Raw (1). The retail `gamedata.sig` verifies against the source's `g_amax_publicKey` when the SHA-1 is taken over the raw on-disk FAT bytes. The engine reader now handles v2 (`PAK_VERSION_READ_MAX 2`, `PakRead.cpp` `ReadFatV2`, codecs take the known stored size via `I_PakCompress::SetKnownPhysicalLength`).
- **The PC code paths in this snapshot were not the shipping ones.** Retail Blur PC (paks dated 2010-04-30) already used pak v2 while this 2010-06-29 tree reads v1. Symptoms fixed so far, all `[Blur2PC]`: audio renderer copied the never-allocated 5-channel surround buffer (`renderer.cpp`); `C_GameWorld::ViewDependentFXUpdate` dereferenced the global colour/depth buffers which are only set under `USE_DISPLAY_WINDOWS` or after `C_ApplicationPC`'s device-reset path succeeds; `C_DamageLayer` never set `m_pDamageVolume` on PC; `C_GameInputManager::GetGameInput` had no bounds check while the UI scripts address pads 0..3 and PC allocates 1 user; a movie renderer whose Bink open failed made `CreateRenderersVolatile` fail and with it the global buffers. Retail `models.pak` does not exist (models are inside `root.pak`); `boot.pak`, `gamedata_boot.pak`, `lut_rampak.pak`, `root_streaming.pak` are not mounted by this source on PC (`.baf` audio banks live in `root_streaming.pak`, hence "Failed to load bank menumusic.baf").
- **PC render path gaps (black frame, fixed 2026-09-23).** Three independent causes, found with an apitrace D3D9 trace (`C:\Tools\apitrace\apitrace-14.0-win32`; `apitrace trace --api d3d9`, then `d3dretrace -s <dir> -S <calls>` snapshots the bound render target at any call): (1) `C_ApplicationBase::RenderSplitscreenViewWithAA` never re-bound the back buffer on PC, so the main view drew into whatever target the pre-render passes left bound (a 512x256 downsample) and the post-process then copied an empty back buffer; (2) `C_HighDynamicRange::CreateLookupTexture` loads the colour-grading LUT with `E_Usage_System`; on PC it is bound to sampler 8 directly and a system-memory texture samples as black, so the tone-map output was black; (3) movie renderer failure blocked the global colour/depth buffers (see above). The in-game "inf FPS" overlay is `GameDebug::C_MiniPerfMonitor` (on by default outside Master, `GameSys.MiniMonitor.Enable`). It does not read the Mercury profiler: it reads `CPU_TIMING`/`GPU_TIMING` stats named `CPU`, `CPU.Update`, `CPU.Render`, `CPU.Present`, `CPU.Update.Physics`, `GPU`, `GPU.Present`; the PC `IdleLoop` did not open the frame-level ones or call `C_CPUTimingStats::UpdateStats`, so CPU total was 0 and FPS = 999/0. `C_GPUTimingStats` had no PC backend. Fixed 2026-09-24 (T063): the PC loop opens the same scopes, and a PC backend in `GPUTiming.cpp` times GPU events with D3D9 timestamp query pairs read 3 frames later (released in `DestroyD3D9`). Neither exists in retail (Master, `CFG_GOLD`, compiles both timing systems out). With decoupled update the Update and Physics rows are non-zero only on frames that ran an update; FPS counts the whole loop including the optional `BLUR2PC_FRAMELIMIT` wait. The profiler bar display (`System.Performance.ShowStats`, `C_DebugHUDPerf`) still needs `ENABLE_MERCURY_PROFILER` (Debug/RelWithDebInfo builds).
- **Built-in shaders need `/Zpr`.** The engine uploads matrices row by row; Bizarre's PC shader scripts compile with `/Zpr` (`mercury/applications/Graphics/TestDisplay/src/mk_common_pc_mesh.bat`). Without it every built-in UI/decal shader got its matrices transposed and drew nothing (invisible UI). `shadergen.py` now passes `/Zpr`.
- **Frame rate: 60 Hz simulation, uncapped interpolated rendering (2026-09-24).** The timer floor was 1/60 s, so above 60 fps the game ran fps/60 times fast; the floor is now 1 ms. The simulation cannot take shorter steps: `RacingPhysics::Car` integrates a hard-coded 1/60 s per step (`car.cpp`, `CreateGravityCache` sets `m_dd.frameTime = 1/60`), and much per-frame game logic (vehicle `FakePhysics` forces added per frame, pickup/decoy/reverse-nitro rotations, input auto-repeat, light trails) assumed one frame per step, as the Aib0t write-up found. So the PC loop (`C_Application::IdleLoop`, ApplicationPC.cpp) now decouples update from render: the game update runs only when 1/60 s of real time has accrued, consuming whole ticks (max 4) and reporting exactly that time to the game through the timer's forced frame time (`g_Blur2PCForcedFrameTime`), so every update runs whole 60 Hz steps; every loop iteration renders. Rendered frames between updates blend poses: `WorldRender::C_ModelInstance::SetElementMatrix` records each element matrix's previous-tick and current-tick values; before a render the ones that moved on the latest tick are written as a blend (quaternion slerp, linear position and scale; jumps over 20 m are not blended) and restored after it. The camera uses its existing motion-blur interpolation (`C_Camera` previous pose, `I_Feed::ToViewSetup`) shifted by the render fraction, only for cameras updated on the latest tick. Cost: up to one tick (16.7 ms) of display latency. Measured: 144 fps render, 60 Hz update, camera advancing 0.33 m on every rendered frame at speed (previously repeated positions). `BLUR2PC_DECOUPLE=0` restores one update per rendered frame; `Framework.Timer.FrameLimit` / `BLUR2PC_FRAMELIMIT` caps rendered fps (default 0, uncapped). Car blob shadows are interpolated too: `C_DynamicBlobShadowInstance::UpdatePosition` keeps the previous and latest caster pose and ground point, and `C_BlobShadows::PreRender` blends them with the same fraction (`WorldRender::Blur2PCInterpRenderAlpha`). Not interpolated yet: particles, headlight projections and HUD markers stay at the latest tick, so they can lead a moving car by up to one tick. **Body/wheel jitter (fixed 2026-09-24):** vehicle parts store their world matrices through `C_Part::m_pWorldMatrix` (Component.cpp), bypassing `SetElementMatrix`, so only the wheels were blended and the body sat one tick ahead; the interpolation registry is now keyed by destination matrix address (`Blur2PCInterpRecordStore`) and the part store path records too. **Body-vs-parts jitter and photo-mode camera swings (fixed 2026-09-24, later):** two more paths bypassed the blend. (1) `C_VehicleActor::DeferredUpdate` writes the body's element matrices (every non-wheel element, `m_WorldMatrices`, VehicleActor.cpp ~750) straight into material data, so the body drew at the latest tick while doors, bumpers and wheels drew blended; those stores are recorded now (`m_Blur2PCWorldMatrixOwners` keeps the owning model instance per pointer). (2) The camera blend used `C_Camera::m_PrevPosition`, which is a motion-blur input in this engine: `C_VehicleFeed::SetMotionBlur`, `C_AmaxChaseCamera::SetMotionBlur` and `C_CameraSystem::Update` (photo camera: `Position() - MotionBlur()`) overwrite it every update with an artificial blur vector, so in photo mode the view swung along the user's blur setting every frame. `C_Camera::GetPrevPosition` now also captures the real previous-update pose (`m_Blur2PCPrevPosition/Shaken/Fov`), and `I_Feed::ToViewSetup` computes the motion-blur matrices exactly as before and then shifts them by the delta from the latest pose to the render-fraction pose on that real line, so the blur inputs are untouched. **AI rims, animated meshes (fixed 2026-09-24, later still):** `C_VehicleActor::SynchData` stores the tyre, alloy rim, brake disc and brake caliper matrices raw through the part's world-matrix pointer (VehicleActor.cpp ~5064-5084); recorded now. Animated models (`AnimatedModel::C_AnimatedModelInstance::Update` and `SetJointTransformParameters`: drivers, animated special-effect meshes such as the vehicle-attached pickup effects, animated level objects) write element and skinning matrices raw, and they do it from update tasks that `C_GameWorld::BeginFrame` flushes inside the render (`C_ApplicationBase::CommonRender`), after the blend pass. The registry gained `Blur2PCInterpRecordTickStore`/`...43` for stores that belong to the current tick even when issued inside a render: the value is recorded and the blend written immediately, then restored after the render like the rest; skinning palettes (`MathsStorage::MatrixRow43`, three float4 columns) are supported as a second destination layout. Plain stores inside a render (`C_ModelSingleElementRender::UpdateElementMatrix` and similar render-time writers) keep the old rule and are left alone. Still at the latest tick: particle emitter transforms and flare nodes set by `C_ParticleSpecialFXInstance::UpdateWorldMatrix`/`C_FlareSpecialFXInstance::UpdateWorldMatrix`. **Pickup display behind the car (fixed 2026-09-24, later):** it is the HUD gadget `UIPerks2` (`hud_objects` / `Perks_Dummy`, single-viewport only), drawn as world-space sprites; `UIPerks2::Render` places its parent gadget at the vehicle logic actor's world matrix on every rendered frame, i.e. the latest tick, so it led the blended car by up to one tick. `C_VehicleActor::Blur2PCRenderMatrix()` now returns `m_Matrix` blended between the last two ticks with the render fraction (kept by `DeferredUpdate`; `m_Matrix` outside a render or after a teleport), and the gadget uses it on PC. The other HUD gadgets that read `C_VehicleLogicActor::GetWorldMatrix()` per frame (`UIAiHud`, `UITargeting`, `UIMiniMap`, `UIRaceLine`, `UIFanMessage`) still use the latest tick; switch them to the same call if they show it. The first attempt (gadget reading the blended matrix in `Render`) had no effect because the UI builds its sprite lists in `C_UiManager::Process` during the game update; the working fix gives the car-attached gadget (player 0) its own sprite panel `E_GameSpritePanel_VP0_CAR`, whose world-to-device matrix `C_UiManager::PreRender` pre-multiplies each frame by the delta from the car matrix the sprites were built with to `Blur2PCRenderMatrix()` (`UIPerks2::Blur2PCCarPanelDelta`); confirmed by the user. **Car light flares (2026-09-24):** `C_VehicleActor::UpdateLightFlares` (flare `C_Node` positions read by the light-effect manager at render), `UpdateAuxFlares` (`C_AuxFlareInstance` position/direction) and `UpdateDynamicLights` (rear point light) place from `m_Matrix` during the update, so at speed they led the drawn car along its direction of travel (seen from the chase camera as flares riding up). The registry gained render hooks (`Blur2PCInterpAddRenderHook`, called after the blend pass and before the restore); each vehicle actor registers one that re-places those three from `Blur2PCRenderMatrix()` for the frame and restores the update values after it (`C_VehicleActor::Blur2PCPlaceLights`). Headlight projection (`UpdateHeadlights`) is not covered yet. The Aib0t write-up's final solution gates `C_GameWorld::Update` to a fixed tick (30 Hz there) with buffered debounced input and no interpolation, so frames between ticks repeat the last tick's poses; the user wants rendered motion above 60 Hz, so this port keeps the interpolation and its per-consumer hooks.
  - **Wheel spin and car-attached UI under the decoupled loop (T114, 2026-09-26).** (0) *Blurred rims never blended (the rims the user saw jump about a metre ahead of AI cars).* At speed `C_WheelBlur` shows the blurred spokes element (`E_PartCode_AlloyBlur`, wheel model `m_pWheelModelResource`) in place of the plain alloy. Each tick `C_PartList::UpdateMatrices` first stores that element's part-local matrix (translation about (-0.08, 0, 0)) into its world-matrix slot, and `SynchData` then overwrites it with the world wheel matrix (`SetElementMatrix(-1)` on the alloy instance). The registry's teleport rule (no blend after a jump over 20 m in a tick) was judged on the first store of the tick, a 130 m jump from last tick's world position, so that element was never blended and drew at the latest update, up to a tick's travel ahead of the car. The rule is now judged at blend time on the tick's final value (`CanBlend`). Measured on an AI car's front-left wheel over 619 renders: tyre, rim, alloy, blurred alloy, disc and body each blended on 617 (the other two precede the first previous tick); before the change the blurred alloy blended on none. (1) *Wheels.* The drawn wheel matrix is the rotor's orientation (`CarWheel::GetRotationMatrix`), turning about its local X. `CarWheel::RotationScale` makes the rotor spin slower than the road speed implies at speed ("to improve high-speed stability"), so in a normal 60 Hz tick it turns at most ~1.55 rad (measured, player car, 15 s drive). The decoupled loop merges ticks when a frame runs long (updates of 2-4 ticks; the perf overlay showed "update 36.8 Hz" on a loaded machine), and a 2-tick update turns a wheel ~3.1 rad or more; at standstill wheelspin `RotationScale` is 1 and the rotor is unscaled. Past pi per update, `BlendMatrixImpl`'s shortest-arc slerp turned the tyre, rim, disc and alloy backwards between ticks, so rims visibly spun back and forth (AI cars side-on). `Blur2PCInterpRecordWheelStore` / `C_ModelInstance::Blur2PCSetWheelElementMatrix` (from `C_VehicleActor::SynchData`) record the wheel matrix and the rotor's spin about the axle (`GetRotor().AngularVelocity()` dotted with the wheel's X, rad/s); the blend takes the measured turn between the two ticks, unwrapped to the whole number of turns nearest spin x the update's game time (`Blur2PCInterpSetTickSeconds`, the forced frame time), and blends only the remainder. Check of the estimate: drawn turn against spin x tick, same sign, median difference 0.027 rad once rolling; on the grid (wheels rocking) the two disagree, but those turns are far below pi. (2) *UI that follows a car.* The UI builds its sprite lists once per update from the car's update pose; the render draws the car blended. `UICarNode` (the race-start countdown `CountdownNode1-3`, `hud_objects`, `CDText` in panel `_VP0`) is placed at the player's `C_VehicleLogicActor::GetWorldMatrix()` in `FrameUpdate`, and `UIAiHud` places each AI car's badges (name, position, damage, perks, targeting) at the car's collision-body position, facing the update camera; both led the drawn car by up to one update, so they jittered against it. The 3D UI panels already project with the per-frame interpolated camera (`C_ApplicationBase::SetupViews` runs at the start of each render, before `C_UiLayer::RenderOnce` calls `C_UiManager::PreRender`). Fix: `C_Simple2D::Blur2PCSetAnchor` registers a gadget for the current sprite lists with the car's update matrix; `C_GadgetBase::CalcTransformHierarchy` notes every post-transform pool entry popped by the anchor or its descendants (children render through their own Render message, so the parent chain is walked); per rendered frame `C_UiManager::PreRender` -> `UIAiHud::Blur2PCPlaceCarSprites` -> `C_Simple2D::Blur2PCPlaceAnchored` rewrites those entries from their saved values moved by the car's update-to-render delta (`C_VehicleActor::Blur2PCRenderMatrix`): the whole rigid move for `UICarNode`, translation only for the camera-facing badges. Measured in a race: 3 countdown anchors (key 0, rigid) and 16-19 badge anchors, 35-44 entries, moved 0.03-0.4 m per frame (badges) and up to 1.3 m (countdown node). `UIPerks2` keeps its own panel shift (`E_GameSpritePanel_VP0_CAR`). - **Single-instance guard (fixed 2026-09-24).** Without one, launching a second `Amax.exe` starts to a black screen instead of failing cleanly (two processes fight over the same D3D9 adapter/window). Read retail Blur.exe 1.2 with Ghidra (`code/tools/ghidra_retail`) to find its mechanism: very early in `WinMain` it calls `OpenMutexA(MUTEX_ALL_ACCESS, FALSE, "BlurMutex")`; the collision branch (`FUN_01efe771`, reached by a manually-pushed return address into a JMP-through-IAT tail call, not a plain `CALL`) hands off into a runtime bytecode interpreter (`FUN_01fc9113`: `cpuid`, an interlocked spin-wait, a rotate-decode loop, then an indirect call to a computed address) — the signature of a commercial DRM/anti-piracy wrapper (SecuROM-style), not Bizarre Creations' own source, and not something to reverse-engineer or reproduce. The portable facts are the mutex name and the exit: retail's rejected instance, measured live (retail runs on this machine through the DXVK `d3d9.dll` in its folder), exits with **code 0** after ~1.2 s and never creates a window. `code/mercury/library/gamesys/framework/include/framework/application/ApplicationMain.inl`'s PC `WinMain` now opens `CreateMutexA(NULL, FALSE, "BlurMutex")` before anything else and, on `ERROR_ALREADY_EXISTS`, does a plain `return 0` (ours: 72-92 ms, exit code 0, no window). An earlier `ExitProcess(1)` stand-in was removed: it skipped `DLL_PROCESS_DETACH` for every loaded DLL and only existed to dodge a real bug, `Game::C_ReplayDirector::Destroy` (`ReplayDirector.cpp:129`) dereferencing `m_Vehicles[i]` without a null check while every slot is still NULL (the constructor nulls them; nothing populates them until a race), which crashed any exit before the game initialised. That loop is now guarded like the `SAFE_DELETE_PTR` members beside it. Not confirmed against retail's bytes: RTTI is stripped (no type descriptor for the class, `FindRttiClass.py`), and the function has no string anchors; the justification is that a shipped build cannot crash on every quit-to-desktop before a race, so retail's compiled code guards it one way or another. **The ~100 ms "window outline and shadow" on every launch (rejected or not) is not the game's window.** A system-wide top-level `HWND` watcher at 0.1 ms resolution plus an in-process `WH_CBT` hook installed from an `init_seg(lib)` static (live 3 ms before `WinMain`) both show the rejected instance creates no window in any process; launching through `play.bat` instead creates a **Windows Terminal** console-host window (`CASCADIA_HOSTING_WINDOW_CLASS`, 1920x1025 at its default position, ~240 ms) for `cmd.exe`, whose frame and shadow render before its contents, and it closes when the batch exits. Retail is launched directly and never gets one. `DisableProcessWindowsGhosting()` was tried and removed (it only affects an existing unresponsive window). Fix: `Blur.lnk` in the repo root starts `_work\run\Amax.exe` directly with the Blur install as Start-in, the retail launch shape; `play.bat` stays for `play_complete_career.bat` (environment variable) until T006 makes launchers unnecessary. ### Audio output (PC) (T144, 2026-09-27)

Retail Blur.exe 1.2 imports DSOUND.dll and ships no OpenAL. Retail's debug values are read from `User\debug_values.xml` then `debug_values.xml` in the data folder; only Persist values are written back (to `debug_values.xml`), and the engine values are not Persist.
- Not recovered: the DRM-relocated helper Init calls on the device list (0x00547af0 -> 0x0053b560, ported as Clear). The float-to-int rounding of the decoders' sample counts follows this build's compiler, not retail's x87 code.
