# Analysis: source, discs and engine facts

Facts established by reading the source and the discs. Add to this file when you learn something; date the addition. Nothing here is a plan or a decision (see `plan.md`, `decisions.md`).

## 1. The source (`code/`)

- Byte-identical copy of `C:\AIProjects\Blur\code` (20,770 files). Blur 1 PC snapshot: newest dated artefact is the Xlast header of 2010-04-22, newest bug comment 2010-03-22, all mtimes 2010-06-29. XT pack list is Blur 1 retail plus "DLC Pack Offer E". It predates all five discs.
- Build: VS2008 makefile project driving Jam (`z:\tools\common_bin\jam -sTARGET=WIN32 -sBUILD=Speed`). Jam sources are in `code/tools/jam` and `code/tools/jamplus`. The custom rules used by every jamfile (`SupportedTargets`, `IncludePath`, `Define`, `CheckXDKVersion`, `LINKLIBS`, `PCLIBS`) are defined nowhere in the tree. Expected SDK versions: Xbox 360 SDK 2.0.11164.2, PS3 SDK 310.001, DirectX SDK via `$(DXSDK_PATH)`.
- Missing vendor tree `$(TOP)/libs/vendor`: Bink 1.9r (only `binktextures.h` survives in `graphics/movie`), OpenAL 1.1, Massive ad client 3.7.1.106. Present: Demonware 2.0 libs for win32-vs8, xenon-vs8, ps3-sn; lua; zlib; libtomcrypt/libtommath; cxxtest; tclap.
- Machine state on 2026-09-23: no VS2008, no DirectX SDK, VS 18 present under `C:\Program Files\Microsoft Visual Studio\18`.
- Dropped dependencies (user, 2026-09-23): **Bink** is removed, not replaced; the discs' 31 `ui/movies/*.bik` are Blur 1 tutorial/attract/splash clips, nothing Blur 2 specific. The movie player must report "finished" immediately so splash/attract/tutorial screens fall through. **Massive** (Massive Inc. in-game advertising SDK, `ENABLE_MASSIVE` in `gamesys/advertising/AdvertManager.h`, wrapper `Advertising::` called from `GameApp.cpp`, `AmaxWorldLayer.cpp`, `GameWorld/View/Main.cpp`) stays undefined; hoardings keep their default textures. The `AdClientLog.txt` on every disc is its log.
- Platforms: `PLATFORM_PC` / `PLATFORM_XENON` / `PLATFORM_PS3` (+SPU). PC graphics is D3D9 only (`DeviceDefines.h` forces `GRAPHICS_D3D9`, `SHADERS_HLSL`, `DEVICE_PCD3D9`); D3D10 folders exist but nothing selects them.
- "Kanzen" in the source is just a namespace: Hollywood/third-person cameras in `amax/library/Kanzen`, `Kanzen::C_VLC_Sensor`, damping utilities. It carries no date information.

### Build description extracted from the jamfiles (T002, 2026-09-23)
- Tool: `code/tools/jam2cmake/jamextract.py`, a Python interpreter for the Jam subset the jamfiles use plus Bizarre's custom rules. Run from the repo root: `python code/tools/jam2cmake/jamextract.py --top . --root code/amax/game/jamfile.jam --target WIN32 --platform PC --build Speed --out _work/build/targets_pc_speed.json` (and `--build Debug`). Output: one JSON with every target (kind, dir, sources, PCH source, PCH headers, include dirs with existence flags, defines), per-file `object_defines`, `cpfiles`/`importcp` (shader-constant header generation), the Lua bundle list (137 scripts), final `LINKLIBS`/`LINKFLAGS`, and diagnostics.
- Result for WIN32/PC: 70 targets (1 application `Amax`, 69 libraries), 2,449 unique source files, 76 jamfiles visited. Speed and Debug differ only in link inputs (Demonware release-mt vs debug-mt) and `GameDataLogging.cpp` (absent in Master only).
- Rule semantics that had to be inferred (each verified by the resulting file lists): `SubDir` resets per-directory state including every `*SRC` variable (otherwise `movie`'s `PCSRC` leaks into every later library through `$($(PLATFORM)SRC)`); `IncludePath`/`Define`/`SUBDIRHDRS` are per-directory and snapshotted by `Library`/`Application`; relative sources resolve against `SUBDIR`, then its parents (`amax/game/GameAudio/jamfile.jam` lists files relative to `amax/game`); `SubInclude` is immediate and a jamfile is evaluated once per run; `LINKLIBS`/`LINKFLAGS` are global and read at link time, so the final values apply.
- Configuration macros come from the build system: exactly one of `BUILD_CONFIG_DEBUG | RELEASE | PROFILE | SPEED | MASTER` (`core/Core.h` derives `CFG_DEBUG`, `CFG_RELEASE` (+`CFG_ALLOW_OPTIMIZE_OFF`), `CFG_PROFILE`+`CFG_SPEED`, `CFG_SPEED`, `CFG_SPEED`+`CFG_GOLD`). `PLATFORM_PC` is derived from `_WIN32` in `Core.h`, so only the build-config macro is mandatory. Per-target defines from the jamfiles: `USE_SOLVER_2` (game, physics, gamesys libs), `OBJ_SHADERS` (display, render, world_render, ui, debugsystems, shadows), `NGL_GPU_D3D_PC`/`NGL_GPU_D3D`/`NGL_GPU_D3D9`/`NGL_GPU_ONLY` + `FX_ALLOW_INCLUDE` (fx), `RENDERINGDATA_ALLOW_INCLUDE`/`SCENEGRAPH_ALLOW_INCLUDE`, `USE_XAUDIO2` (audio), `XT_GAME` (xtgame), `LTM_DESC`/`LTC_SOURCE` (libtomcrypt, security), `ANIMATION_ALLOW_INCLUDE`, `LOGFS_ENABLE` + `CFILESYSTEM_CREATE_FUNC_ENABLED` (game, non-Profile/Master), `CREATE_CROWD_FLAG_RENDERER`. Per-file: `SPU_NET_TASK` on RacingPhysics `car.cpp`/`networkupdate.cpp`; `DEFLATE_MODULE`/`INFLATE_MODULE` on `PakCompressPacketZLib.cpp` (SPU-only builds; on PC the file is compiled once, plain).
- Link inputs on PC: `secur32 crypt32 ws2_32 dbghelp psapi`, DirectX SDK `dxerr d3d9 d3dx9 dinput8 dxguid xinput`, OpenAL 1.1 `OpenAL32`+`EFX-Util`, Demonware 2.0 (`bdConnection bdCore bdLobby bdSocket bdPlatform bdNet bdExampleCommonLobby ssleay32 libeay32 libcurl`, present in tree), Bink `binkw32`, Massive `xmassiveadclientlogging`. Flags `/SUBSYSTEM:WINDOWS /MACHINE:X86 /DEBUG /NODEFAULTLIB:LIBCMTD /NODEFAULTLIB:LIBCMT` (so the CRT is the DLL runtime). x86 only.
- Gaps the JSON reports: one stale PCH reference (`amax/library/Kanzen/jamfile.jam` names `StdAfx.cpp`; the files are `Kanzen_PCH.cpp/.h`); 18 missing include dirs, all explainable: `Amax$(_PLATFORM)` (empty on PC), `Code/Genesis/Library/include` (dead), `Advertising/IncludePath` (jamfile typo), `common/ai/air/include` (wrong path in one jamfile), and the vendor dirs Bink, Massive, OpenAL, `libs/vendor/jpeg/version62` (IJG libjpeg 6b, needed by `JpegHelper`). Library `Jpeg` is linked but has no jamfile in the tree.
- Generated headers: `CPFile x.cp|.cv|.sp` produces `x.h` next to the source with `#define CP_NAME n` + `#define CCP_NAME cn` (`.cp`, pixel constants), `CV_`/`CCV_` (`.cv`, vertex constants), `SP_`/`SSP_` (`.sp`, samplers; used as `register(SSP_...)`). Directives: `#set N` (counter), `#begin N` … `#end`, `#align N`, `#include "other.cp"` (chains parent module constants), `#skip`. `ImportCP header : TOP … Module` copies a generated header from another module into the current one. A reference output exists at `code/tools/spt_billboard/source/spt_billboard/shaders/{ps,vs}Constants.h`. 12 CPFile and 26 ImportCP records are in the JSON; the generator is T003 work.
- **`[ Batch files : StdAfx.h ]` was a unity build.** Each Batch group compiled as one translation unit: `SP_Rewards.cpp` calls a template that is only defined in `SP_SaveGame.cpp`, 190 files earlier in the same group, and hundreds of headers assume includes that an earlier file in their group provided. Nearly every library uses it (amax_gamelogic: groups of 10/2/6/195/7 files; gravity: 37 small groups). `gen_cmake.py` reproduces it with one generated `_work/build/gen/unity/<target>_batchN.cpp` per group (`--no-unity` compiles files individually, which needs many more include fixes).
- **`PLATFORM_PC` must be defined on the command line.** Every PCH header tests `#if defined(PLATFORM_PC)` for its Windows block (winsock2.h before windows.h, time.h) *before* it includes `core/Core.h`, the only place that derives it from `_WIN32`. Without the define the PCH skips winsock2 and the later `#include "stdafx.h"` in each source produces winsock/winsock2 redefinition errors. The original vcproj defined it; CMakeLists does too.
- Shaders: the jamfiles build `.fx` effects (`Effects`/`AmaxEffect` rules, 0 on PC in this extraction because the rule bodies are shader-farm specific) and `.psh`/`.vsh` objects (`OBJ_SHADERS`). Retail PC data already ships the compiled `.fxb` set, so M1 does not need the shader build.

## 2. Engine facts that constrain the port

### File system and paks
- Single global `Sys::I_FileSystem*`; in game it is `LogicalFs::C_OverlayFs`. Layers: 0 = loose cwd ("CFileSystem"), then paks mounted by `C_GameSystems::CreateFsLayers` (`amax/game/GameSystems.cpp` 201-265, `USE_NEW_PAK_LAYOUT`). Layer types `E_Type_Overlay` (first hit top-down), `E_Type_Opaque`, `E_Type_Newer`. In non-gold builds `Util.LogicalFs.OverlayFs.MasterDiscEmulation=false` makes every layer Newer, so a newer loose file overrides a pak copy.
- Choke point: `C_OverlayFs::GetBestLayer()` (`util/logicalFs/overlayfs/OverlayFs.cpp` ~488/571). Also `InsertLayer`/`AddLayer` for a new top layer. `Util.LogicalFs.OverlayFs.FileMappingDebug` logs every path-to-layer mapping.
- PC mounts: `cache/root.pak` at `/`, `cache/models.pak` at `/models/`, `cache/shaders-speed.pak` at `/graphics/shaders/speed/`, `cache/gamedata.pak` at `/gamedata/` (RSA-1024 signature `gamedata.sig`, key `g_amax_publicKey`, SHA-1 per file). Not mounted on PC: `root_streaming.pak`, `boot.pak`, `boot_rampak.pak`, `gamedata_boot.pak` (all inside `#ifndef PLATFORM_PC` in `BootLayer.cpp`). `lut_rampak.pak` is gated only by `g_enableLutRamPak`.
- Pak format (`util/logicalFs/pakfs/impl`): `PAK2` fourCC + version + sector size; `C_PakHeader` (SHA-1, codec, fat entry type, separator, meta string offset); XOR-obfuscated string table (key in `PakUtil.cpp`); FAT of `C_PakFatEntry` (32 bytes) or `C_PakFatEntrySecure` (+SHA-1), sorted by CRC. Codecs: Raw, ZLib, XMem, PacketZLib, PacketXMem. Hash: `C_PakCrc32`, poly 0xEDB88320, init 0xFFFFFFFF, no final XOR, over the normalised lowercase path with leading separator. Matches Blur2Test's `~crc32("\\" + path.lower())` on 29,913 of 29,913 records.
- I/O: PC `IoDevice.cpp` uses `CreateFile` with `FILE_FLAG_NO_BUFFERING` (sector-aligned reads). `C_LogFs` wrapper logs every access to `./user/logfs` in non-gold builds.
- **Pak version 2** (T005, 2026-09-23). The source reads version 1 only (`PAK_VERSION 1`); retail PC ships v2 for every pak except `shaders-speed.pak` (v1); Nov discs use v2 for `gamedata.pak` and v3 for `root.pak`. v2 layout, verified on all 7 retail PC paks: pre-header `PAK2`/version/sectorSize as v1; then U32 headerSize = 0x20 and a **packed** 32-byte header `{codec, fatEntryType, separator, unused, U32 codecFlags, U32 metaStrOffset, U64 fileTime, U32 stringTableBlockSize, U32 fatBlockSize, U32 unknown}` (no 20-byte integrity hash; the last word holds leftover characters such as `bin`, `ss`, meaning unknown). String table (U32 size + XOR-crypted names, padded to a sector) starts at **sector 1**, the FAT (U32 count + U32 bytes + entries) right after it, both block sizes sector-aligned as the header says. FAT entries are 40 bytes: the v1 32 bytes (crc, string offset, parent FAT offset in on-disk strides, logical length, U64 file time, U64 start sector) plus `U32 unknown` (per file; not the path CRC, not SHA-1 of stored or logical bytes) and `U32 storedSize`; secure entries append U32 padding + SHA-1 (64 bytes). Payloads have **no stored-size prefix** (v1 had one, not counting itself): ZLib streams start at the sector, PacketZLib starts with the U32 chunk cap 0x10000 then `[U32 size][data]` chunks, Raw is the bytes. The secure SHA-1 is over exactly `storedSize` bytes from the payload start. Retail codecs: root/boot/lut_rampak = PacketZLib (4), gamedata/gamedata_boot = ZLib (2) secure, root_streaming = Raw (1). The retail `gamedata.sig` verifies against the source's `g_amax_publicKey` when the SHA-1 is taken over the raw on-disk FAT bytes. The engine reader now handles v2 (`PAK_VERSION_READ_MAX 2`, `PakRead.cpp` `ReadFatV2`, codecs take the known stored size via `I_PakCompress::SetKnownPhysicalLength`); v3 is not implemented (not needed: Nov paks are extracted by Blur2Test).
- **The PC code paths in this snapshot were not the shipping ones.** Retail Blur PC (paks dated 2010-04-30) already used pak v2 while this 2010-06-29 tree reads v1, so the Kanzen branch forked before the PC release work landed. Symptoms fixed so far, all `[Blur2PC]`: audio renderer copied the never-allocated 5-channel surround buffer (`renderer.cpp`); `C_GameWorld::ViewDependentFXUpdate` dereferenced the global colour/depth buffers which are only set under `USE_DISPLAY_WINDOWS` (Xenon/PS3) or after `C_ApplicationPC`'s device-reset path succeeds; `C_DamageLayer` never set `m_pDamageVolume` on PC; `C_GameInputManager::GetGameInput` had no bounds check while the UI scripts address pads 0..3 and PC allocates 1 user; a movie renderer whose Bink open failed made `CreateRenderersVolatile` fail and with it the global buffers. Retail `models.pak` does not exist (models are inside `root.pak`); `boot.pak`, `gamedata_boot.pak`, `lut_rampak.pak`, `root_streaming.pak` are not mounted by this source on PC (`.baf` audio banks live in `root_streaming.pak`, hence "Failed to load bank menumusic.baf").
- **PC render path gaps (black frame, fixed 2026-09-23).** Three independent causes, found with an apitrace D3D9 trace (`C:\Tools\apitrace\apitrace-14.0-win32`; `apitrace trace --api d3d9`, then `d3dretrace -s <dir> -S <calls>` snapshots the bound render target at any call): (1) `C_ApplicationBase::RenderSplitscreenViewWithAA` never re-bound the back buffer on PC (Xenon/PS3 do it through `USE_DISPLAY_WINDOWS` `SetWindow`), so the main view drew into whatever target the pre-render passes left bound (a 512x256 downsample) and the post-process then copied an empty back buffer; (2) `C_HighDynamicRange::CreateLookupTexture` loads the colour-grading LUT with `E_Usage_System` because on PS3 (`TONEMAP_COMBINE`) it is only read by the CPU; on PC it is bound to sampler 8 directly and a system-memory texture samples as black, so the tone-map output was black; (3) movie renderer failure blocked the global colour/depth buffers (see above). The in-game "inf FPS" overlay is cosmetic: it reads the Mercury profiler, which `ProfilerEnable.h` compiles out in Speed builds.
- **Built-in shaders need `/Zpr`.** The engine uploads matrices row by row; Bizarre's PC shader scripts compile with `/Zpr` (`mercury/applications/Graphics/TestDisplay/src/mk_common_pc_mesh.bat`). Without it every built-in UI/decal shader got its matrices transposed and drew nothing (invisible UI). `shadergen.py` now passes `/Zpr`.
- **Frame rate: 60 Hz simulation, uncapped interpolated rendering (2026-09-24).** The timer floor was 1/60 s, so above 60 fps the game ran fps/60 times fast; the floor is now 1 ms. The simulation cannot take shorter steps: `RacingPhysics::Car` integrates a hard-coded 1/60 s per step (`car.cpp`, `CreateGravityCache` sets `m_dd.frameTime = 1/60`), and much per-frame game logic (vehicle `FakePhysics` forces added per frame, pickup/decoy/reverse-nitro rotations, input auto-repeat, light trails) assumed one frame per step, as the Aib0t write-up found. So the PC loop (`C_Application::IdleLoop`, ApplicationPC.cpp) now decouples update from render: the game update runs only when 1/60 s of real time has accrued, consuming whole ticks (max 4) and reporting exactly that time to the game through the timer's forced frame time (`g_Blur2PCForcedFrameTime`), so every update runs whole 60 Hz steps; every loop iteration renders. Rendered frames between updates blend poses: `WorldRender::C_ModelInstance::SetElementMatrix` records each element matrix's previous-tick and current-tick values; before a render the ones that moved on the latest tick are written as a blend (quaternion slerp, linear position and scale; jumps over 20 m are not blended) and restored after it. The camera uses its existing motion-blur interpolation (`C_Camera` previous pose, `I_Feed::ToViewSetup`) shifted by the render fraction, only for cameras updated on the latest tick. Cost: up to one tick (16.7 ms) of display latency. Measured: 144 fps render, 60 Hz update, camera advancing 0.33 m on every rendered frame at speed (previously repeated positions). `BLUR2PC_DECOUPLE=0` restores one update per rendered frame; `Framework.Timer.FrameLimit` / `BLUR2PC_FRAMELIMIT` caps rendered fps (default 0, uncapped). Car blob shadows are interpolated too: `C_DynamicBlobShadowInstance::UpdatePosition` keeps the previous and latest caster pose and ground point, and `C_BlobShadows::PreRender` blends them with the same fraction (`WorldRender::Blur2PCInterpRenderAlpha`). Not interpolated yet: particles, headlight projections and HUD markers stay at the latest tick, so they can lead a moving car by up to one tick. **Body/wheel jitter (fixed 2026-09-24):** vehicle parts store their world matrices through `C_Part::m_pWorldMatrix` (Component.cpp), bypassing `SetElementMatrix`, so only the wheels were blended and the body sat one tick ahead; the interpolation registry is now keyed by destination matrix address (`Blur2PCInterpRecordStore`) and the part store path records too.
- **Controls on PC.** `C_ControlConfig::RemapGameControls` replaced every driving binding with Xbox pad buttons when a profile loaded, dropping the keyboard; it now combines keyboard + pad (`C_RemapCombiner`). The keyboard menu map follows retail Blur PC, read with Ghidra (`code/tools/ghidra_retail`): retail `SetupAmaxUserControls` is `0x00415a30`; its menu table at `0x00e653b8` has rows {button, key, split-screen key, pad button} and retail key numbers equal this source's `C_Keyboard` enum (DirectInput scan code - 1). Single-keyboard layout: Confirm = Enter + Space, Cancel = Esc, Option1 = Right Shift, Option2 = Right Ctrl, Left/Right trigger = Page Up/Page Down, Left/Right shoulder = Insert/Delete, Right thumb = Delete, Start = F1 + Esc, Back = F2, nothing on the plain d-pad buttons; menu stick axes A/D, S/W (down key first), arrows for the right stick; arrows on the pad-or-stick directions (unchanged). The snapshot had V/B for Confirm/Cancel, Enter for Start, Esc for Back. Menus act on Cancel, not Start, so F1 has no visible effect there. **Escape never reached the game in this snapshot**: `C_KeyboardPC::Update` kept keys with `ConvertFromDirectInputKey(i) > 0`, and Escape is index 0; retail's keyboard update (`0x00845360`) tests `>= 0`. Fixed the same way. `Framework::AddButtonInput` now sets the input when the button has none (the combiner asserted on NULL). The window shell (`C_Application::MyKeyDown`) closed the window on Escape; removed. DirectInput keyboard is foreground-only. Retail keyboard driving keys come from a per-profile custom table (Lua `SetCustomKeyboardControls`, fields Throttle/Brake/EBrake/ChangeView/RearView/Pause/SwitchPerk/.../SteerLeft/SteerRight) and default tables at `0x00e64f98`/`0x00e65100`; not ported.
- **AI never ran.** (1) The Showroom has no `.aid`, and that failure cleared `AmaxAIR::m_SystemsInitialised`, so later `LoadAICityData` calls were skipped. (2) `InitTrackDataSystem` cached the track-data interface before the object existed (NULL), so `AllOK()` was false and the AI update never ran. (3) Race logic looked for splits via `GetTrackDataSystem()`, which is NULL until `InitRace`; it now uses `GetLoadedTrackDataSystem()`. After (1)-(3) the splits are found; AI cars on track not yet confirmed visually.
- **Vehicle damage rendering (fixed 2026-09-24).** Retail PC vehicle shaders (`shaders-speed.pak`) are built with `_DAMAGE_USE_F32`: the vertex damage volume (vertex stage 257) is added to the position unscaled, so PC now creates it as A32B32G32R32F (`BLUR2PC_DAMAGE_VOLUME_F32` in `DamageLayer.cpp`; this removed the dents), and FX binds a zeroed 1x1x1 volume where it would bind its 2D default on a vertex sampler. The scratched/undercoat paint came from constants: the retail paint vertex shaders read `c203.w` as the dent amount and `c204.w` as the scratch level (`mul o3.w, r0.x, c204.w`; `mad r0.xyz, r0, c203.w, v0`), and those registers are the undercoat and scuff colours, which this source uploads with w = 1 (fully damaged). `VehicleModel.cpp` now uploads both with w = 0. Consequence: per-part race damage is not shown on PC; the source that fed those `.w` values in retail is unknown (open).
- **Car shadows (fixed 2026-09-24).** Cars use blob shadows (`BlobShadows`, one dynamic instance per vehicle; drop shadows come from level scene-graph objects, not cars). Two faults on PC: (1) `BlobShadows::RenderScreenShadow` reconstructs world position from the context's depth texture, the global R32F buffer from `Render::CreateGlobalDepthStencilBuffer`, which nothing on PC wrote; `C_MainView::RenderPrepass1` now `StretchRect`s the prepass depth (deferred colour target 1, hardware z/w, the same encoding every deferred consumer decodes) into it. (2) `psScreenBlobShadows.psh` masks cars out with `1 - depth.a` on every non-Xbox target, a PS3 depth-buffer stencil trick; the PC R32F alpha reads 1, so every pixel was masked. `shadergen.py` now passes `/D BLUR2PC=1` to built-in shaders and the PC path uses mask 1 (cars may receive a little of their neighbours' blob shadow; the height falloff limits it). Verified by an A/B run of `scripts/race.txt` with blob shadows disabled: car-sized shadows appear at the grid slots ahead of the player and vanish with blobs off. **Those shadows have no car above them: the AI cars exist and cast shadows but their models are not drawn** (the "no AI cars ahead" issue is a render problem, not placement). **HUD projected on the road (fixed 2026-09-24, matched to retail).** The snapshot defines `_DISABLE_GFX_BUFFERS` on PC (UiLayer.cpp), so the UI's composite/bloom buffers are never made and `C_UiLayer::RenderOnce` draws the HUD through `RenderAA()` with no render target of its own; the blob shadow pre-render (`C_BlobShadows::PreRender`, run just before in BeginFrame) leaves its last blob texture bound, so the HUD landed in a blob texture and the screen shadow pass projected it from the car (mirrored by the shadow-plane mapping; which texture caught it varied with the shadow count, hence intermittent). Retail Blur.exe 1.2 (Ghidra, scripts in `code/tools/ghidra_retail`): its blob pre-render (0x00734e80) also leaves the target bound, so a restore there is not what retail does; instead retail compiles and calls both `CreateFePostProcessBuffer` (0x00c303e0) and `CreateIgPostProcessBuffer` (0x00c30470, size = back buffer / 4, no depth), i.e. the UI buffers are on, and `RenderOnce` (0x00c30d90) binds the composite before drawing. Three further retail differences in that path were found and ported: `IgRenderComposite` (0x00c30c20) clears the colour only (the snapshot's Colour|Depth|Stencil clear is refused by D3D9 when no depth surface is bound, so the HUD accumulated); `IgRenderPost` (0x00c2fb20) keeps the bloom texture and deactivates the manager; `RenderFullscreen` (0x00c305c0) adds the bloom texture, not the composite. `SetupViews` (0x00c30e60) sizes the in-game bloom view from the back buffer / 4 as well. Changes: UiLayer.cpp only (define removed; composite and bloom view sizes; clear; bloom texture kept; full-screen add). Verified: scripted race frames show a clean road and a glowing HUD.
- **32 fps on a 4K desktop (environmental).** Stack samples during a 32 fps spell show the main thread waiting in `Present` inside DWM (`DwmpDxGetWindowSharedSurface`) after the desktop resolution changed to 3840x2160; it comes and goes between runs with no code change. Not a game bug.
- **Profile saves (PC).** This source saves the profile to `SAVE\AMAXSAVE` under the working directory (the retail install when started by `play.bat`): header magic `0xABCDE337`, uncompressed size, compressed size, then a zlib stream written with `Z_FULL_FLUSH` (no end marker), save version 1373. `C_SaveInfoInterfaceProfile::Load` read that little-endian header as big-endian, so every PC save was rejected; fixed. Retail Blur 1 PC (1.2) saves to `%APPDATA%\bizarre creations\blur\save\blursave` with the same container but save version 1378 (53,832 bytes unpacked against 50,999 here); `LoadGameImpl` accepts only its own version, so retail saves are not loadable without a converter for the five format changes (unknown). `BLUR2PC_COMPLETE_CAREER=1` (launcher `play_complete_career.bat`) applies the source's own `SinglePlayer.CompleteAllTiers` + `UnlockAllCars` logic whenever the career loads: 63 events gold, rank 24, 450/450 stars.
- **Automation.** `system/debug/Blur2PCAutomation.h`: with `BLUR2PC_AUTOMATION=<script>` the game reads timed key presses (injected into the DirectInput keyboard state), writes back-buffer PNGs, ignores focus loss and can quit. No focus or desktop capture needed; runs do not disturb the machine's user. Runner: `_work/run/run_script.ps1 -Script <file> [-Trace]`; scripts in `_work/run/scripts/` (`race.txt`, `garage.txt`, `race_idle.txt`, `garage_trace.txt`).
- Logging: `logcfg.xml` is searched in the cwd then the exe directory (`AutoConfigure::GetPath`); `_work/run/logcfg.xml` sends everything to `_work/run/amax.log` (absolute path; the log subscriber opens through the raw file system relative to cwd otherwise).

- **Single-instance guard (fixed 2026-09-24).** Without one, launching a second `Amax.exe` starts to a black screen instead of failing cleanly (two processes fight over the same D3D9 adapter/window). Read retail Blur.exe 1.2 with Ghidra (`code/tools/ghidra_retail`) to find its mechanism: very early in `WinMain` it calls `OpenMutexA(MUTEX_ALL_ACCESS, FALSE, "BlurMutex")`; the collision branch (`FUN_01efe771`, reached by a manually-pushed return address into a JMP-through-IAT tail call, not a plain `CALL`) hands off into a runtime bytecode interpreter (`FUN_01fc9113`: `cpuid`, an interlocked spin-wait, a rotate-decode loop, then an indirect call to a computed address) — the signature of a commercial DRM/anti-piracy wrapper (SecuROM-style), not Bizarre Creations' own source, and not something to reverse-engineer or reproduce. The one portable fact is the mutex name. `code/mercury/library/gamesys/framework/include/framework/application/ApplicationMain.inl`'s PC `WinMain` now opens `CreateMutexA(NULL, FALSE, "BlurMutex")` before anything else and, on `ERROR_ALREADY_EXISTS`, shows a message box and calls `ExitProcess` directly. `ExitProcess`, not `return`/`exit()`: `Game::C_ReplayDirector::s_Instance` is a global static whose destructor (`ReplayDirector.cpp:129`) calls `m_Vehicles[i]->EraseRecording()` with no null check, and every entry is still NULL this early (nothing has run), so a plain return crashes in `execute_onexit_table` during CRT shutdown — a latent bug in the original source, not new here, that only surfaces on an exit before the game ever initialises. Verified: built `Amax.exe`, launched two instances against the retail PC data dir — the second exits immediately (no crash.dmp), the first keeps running normally (screenshot at the start screen, 144 fps render / 60 Hz update). The ghidra_retail toolkit gained `FindImportRefs.py`, `FindStrings.py`, `FindSymbols.py`, `DumpStrings.py`, `ListForward.py`, `ForceDisassembleAndDecompile.py` (disassembly never reached by auto-analysis, e.g. code only entered via a computed return address) for this investigation.

- **Graphics options (PC) (T008, 2026-09-24).** The snapshot's PC start-up was a development shell: a 640x480 resizable window, device defaults (2x AA, vsync), no settings file, no options screen. Retail Blur.exe 1.2 (Ghidra, `code/tools/ghidra_retail`; retail UI scripts extracted from the exe with `unluac`, see below) does the following, now ported (`[Blur2PC]` in ApplicationPC.cpp, ApplicationBase.cpp, D3D9Manager.cpp, DeviceDebug.cpp, PCD3D9Device.cpp, GameProfile.cpp, lua_Amax.cpp, GameDataFinder.cpp and the Lua scripts named below):
  - *Order.* `C_ApplicationBase::Initialise` (0x0084cf50) creates the display manager **before** the PC platform initialise, and `CreateDisplay` (0x0084d140) calls `SetupDisplayResolutions(10000, 10000, A8R8G8B8, None, Tiled)`. `D3D9Manager::Initialise` (0x005b7590) tests multisample None/2/4/8/16 for full screen only (colour X8R8G8B8, then depth D24S8; the source's CFG_GOLD path) and lists every adapter mode of at least 640x480 with the refresh rate it was first enumerated with (0x005b7420 does not compare refresh rates), sorted. Retail's `E_Multisample` values are the sample counts (0,2,4,8,16).
  - *Resolution manager* (global at 0x011437c4): resolution entries `{index, width, height, refresh, multisample, name "%ix%i"}` for every mode (no "Disabled" entry on PC; the size cap is effectively off), multisample entries `{value, name "%ix"}`; lookups by size (0x005a4840) and nearest pixel count (0x020c892d, DRM-relocated but plain code). The DRM section (`.8thSin`) holds relocated functions that are ordinary code reached through push/ret trampolines; `DisasmRange.py` reads them (its file offset is VA - 0x53ec00, unlike `.text`/`.rdata`/`.data` at VA - 0x400c00).
  - *settings.xml.* `PlatformInitialise` (0x0084bc80) first loads `%APPDATA%\Bizarre Creations\<window name>\settings.xml` (0x0084b570): `<application_settings version="1"/>` and `<shared_graphical_settings width height x y multisample windowed vsync graphical_detail/>`, attributes read **by position**, CRLF after each element. Missing file: the primary display's current mode (0x005b7310), full screen, detail 2. The size is clamped to at least 640x480; a size that is not a mode becomes the nearest mode in full screen and "index 0" in a window. The file is written (0x0084a050) on every device reset, detail change and window move of more than 10 pixels. It is the same file retail Blur uses. `BLUR2PC_SETTINGS` overrides the path; scripted runs force windowed and, without the override, never write the file; none of this is retail.
  - *Window.* Client area at the saved x,y and the resolution's size; styles 0x16ca0000 (caption, system menu, minimise, no resize border) or 0x96000000 (popup); icon resource 101 via WM_SETICON (this build has no icon resource). The device is sized to the client area (0x0084a450 also stores the mode's refresh rate in the device params). Cursor hidden in full screen. WndProc (0x0084ae70): Alt+Enter toggles full screen, Alt+F4 closes, full screen refuses SC_MAXIMIZE/SIZE/MOVE/MINIMIZE, screen saver and monitor power-down are refused, WM_SIZING keeps at least 640x480.
  - *Apply* (0x0084ab80): multisample, style change + SetWindowPos, vsync (PresentInterval One/Immediate), resolution (index 0 = nearest mode to the current size in full screen), then the virtual graphical-detail hook (vtable +0xe0) and the device reset (0x0084a240: save, TestCooperativeLevel, destroy renderers volatile, destroy volatile, CreateVolatile, re-setup views, layer Resize message, create renderers volatile). `BeginRender` (0x0084dbe0) calls `UpdateGraphicsSettings` (0x0084bad0) after `CanRender`: it applies changes made through the debug variables `Graphics.Framework.{Windowed,Vsync,GraphicalDetail,Resolution,Multisample}` and follows window moves/resizes. `CanRender` (0x0084a400) = window exists and is not minimised; a lost device goes through the reset.
  - *Options UI.* Retail's UI scripts are Lua 5.1 bytecode embedded in Blur.exe (144 zlib streams after a name table at file offset 0xb9fbf7; the bundle header word is not the source's `IUZB`); decompiled copies are in `_work/retail_lua`. ### Resources and chunk files
- `Resource::C_Manager` keyed by normalised filename; `C_LoadingThread`; states Constructed → InLoadQueue → Loading → PostLoading → Ready → Evicting → Deleted; eviction delay.
- All chunk files: platform FourCC first (`Platform.h`: `PC  `, `360 `, `PS3 `), then `Sys::C_FileBlock` chunks with `C_BlockHeader` {8-byte id, U32 size, U16 count}. `GameResource::ValidatePlatformId` fails hard on a mismatch; a missing FourCC only warns. All reads are `NoEndianSwap`.
- Version constants: level `E_SceneFileVersion_Current`=0; physics 0; levelrender `E_LevelRenderFileVersion_Current`=1 (EffectVariation); model 0; model render 0; `E_ModelDataFileVersion` 0/1; texture 0; light list 1; Gravity physics 10; XT flask 1-2; `SERIALISATION_VERSION`: Target::Scene 1, StreamData 3, ChunkInfo 1, SamplerState 1, Primitive 1, PvsCellData 1, others 0. Only the Arch archive (`binaryarchive.h:285`, debug) and LightList reject newer data; everything else branches on `>=`.

### Level pipeline
- `C_LevelState::Finished` (`GameLogic/Structures/LevelState.cpp` 280-300): `.\levels\%s\level.level`, `.\gamedata\levels\%s`, `.\gamedata\levels\%s\%s.aid`.
- `C_AmaxWorldLayer::Create` (`GameLogic/Layers/AmaxWorldLayer.cpp` 545): level handle load → AI data → `InstantiateLevel` (route mask `1 << routeNumber`) → `LoadActorStudioActors` (`actorpack.xt` via `XtPackOpen`).
- `C_LevelResource` (`gamesys/game_resource/source/LevelResource.cpp`): `.level` = Level{Header, MdlDat, NavDat, Advert, MtaDbg}; `.levelphysics` = `C_PhysicsLevel::Load` Physic{Header, Main, per-route}; `.levelrender` = `WorldRender::C_RenderLevel::Read` Render{Header, Scene, Lights, LS, PVSData, CubePt2, Portals, Crowd}; `.levelstream` = `StreamData::OpenStreamFile`, `StreamManager` loader thread does SetPosition+Read per chunk throttled by `g_maxMbPerSecond`, decompressed by scheduler jobs.
- No `.levelanim` loader exists. Level animation in this source is XT-driven (`shared_actors/source/XtLevelAnimation.cpp`).
- Geometry/textures baked into render+stream, referenced by `ResourceIndex{block,index}` (block -1 = shared). Shared textures by name + U32 hash (`SharedTextureManager::InsertTexture`). Props/vehicles by path string via XT `GameModel.Filename`.

### Shaders
- `FX::GetShaderPath()` = `graphics\shaders\speed\`; `FX::Manager::LoadEffectInternal` opens `.fxb`; `ImportFXB` (`FXB.cpp`) finds the `PCFX` block; `Shaders.cpp` calls `CreatePixelShader`/`CreateVertexShader` on embedded D3D9 bytecode. ### Timing (frame-rate coupling)
Confirmed against https://github.com/Aib0t/write-ups/blob/main/blur-fps-unlock/readme.md:
- `C_GameWorld::CalcNumberOfSteps` (`GameWorld.cpp` 2438): `m_GameStep = (S32)(m_GameFraction * 60 + 0.5)`; 50 Hz variant behind `TimeStep50Hz`. Step loop at 2543 clamps at `Game.MaxPhysicsUpdates` (2 or 4 depending on config) so under 30 fps the simulation slows. Clamp inside the accumulator is commented out (network timers).
- Frame-counted consumers: `C_GameInput::GetButtonAutoRepeat` now counts real held time in 1/60 s ticks on PC. The rest (`Perks.PickupActor.RotationSpeed`, `Perks.NitrousReverse.RotationSpeed`, decoy rotation, vehicle fake-physics forces, camera update message `min(steps, max)/60`) see exactly one 60 Hz step per update under the decoupled loop, which is the retail PC behaviour, so they need no change.
