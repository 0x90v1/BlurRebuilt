# Analysis: source, discs and engine facts

Facts established by reading the source and the discs. Add to this file when you learn something; date the addition. Nothing here is a plan or a decision (see `plan.md`, `decisions.md`).

## 1. The source (`code/`)

**Layout since 2026-09-25 (D16; D10 from 2026-09-24 to then):** each phase is a git branch checked out in its own worktree (`Blur1PC/`, `Blur1Multi/`, `BlurX/`), all with the same layout, `code/` at the root. Every `code/...` path in this file is relative to a phase worktree. A `Blur1Multi/` or `BlurX/` prefix on a path names the branch the file lives on (`blur1multi`, `blurx`); the path inside the worktree is the part after the prefix. "Overlay copy" in older notes means a phase's edit of a base file, now an ordinary edit on that phase's branch.

- Byte-identical copy of `C:\AIProjects\Blur\code` (20,770 files). Blur 1 PC snapshot: newest dated artefact is the Xlast header of 2010-04-22, newest bug comment 2010-03-22, all mtimes 2010-06-29. XT pack list is Blur 1 retail plus "DLC Pack Offer E". It predates all five discs.

### Build description extracted from the jamfiles (T002, 2026-09-23)
- Tool: `code/tools/jam2cmake/jamextract.py`, a Python interpreter for the Jam subset the jamfiles use plus Bizarre's custom rules. Run from the repo root: `python code/tools/jam2cmake/jamextract.py --top . --root code/amax/game/jamfile.jam --target WIN32 --platform PC --build Speed --out _work/build/targets_pc_speed.json` (and `--build Debug`). Output: one JSON with every target (kind, dir, sources, PCH source, PCH headers, include dirs with existence flags, defines), per-file `object_defines`, `cpfiles`/`importcp` (shader-constant header generation), the Lua bundle list (137 scripts), final `LINKLIBS`/`LINKFLAGS`, and diagnostics.
- Result for WIN32/PC: 70 targets (1 application `Amax`, 69 libraries), 2,449 unique source files, 76 jamfiles visited. Speed and Debug differ only in link inputs (Demonware release-mt vs debug-mt) and `GameDataLogging.cpp` (absent in Master only).
- Rule semantics that had to be inferred (each verified by the resulting file lists): `SubDir` resets per-directory state including every `*SRC` variable (otherwise `movie`'s `PCSRC` leaks into every later library through `$($(PLATFORM)SRC)`); `IncludePath`/`Define`/`SUBDIRHDRS` are per-directory and snapshotted by `Library`/`Application`; relative sources resolve against `SUBDIR`, then its parents (`amax/game/GameAudio/jamfile.jam` lists files relative to `amax/game`); `SubInclude` is immediate and a jamfile is evaluated once per run; `LINKLIBS`/`LINKFLAGS` are global and read at link time, so the final values apply.
- Configuration macros come from the build system: exactly one of `BUILD_CONFIG_DEBUG | RELEASE | PROFILE | SPEED | MASTER` (`core/Core.h` derives `CFG_DEBUG`, `CFG_RELEASE` (+`CFG_ALLOW_OPTIMIZE_OFF`), `CFG_PROFILE`+`CFG_SPEED`, `CFG_SPEED`, `CFG_SPEED`+`CFG_GOLD`). `PLATFORM_PC` is derived from `_WIN32` in `Core.h`, so only the build-config macro is mandatory. Per-target defines from the jamfiles: `USE_SOLVER_2` (game, physics, gamesys libs), `OBJ_SHADERS` (display, render, world_render, ui, debugsystems, shadows), `NGL_GPU_D3D_PC`/`NGL_GPU_D3D`/`NGL_GPU_D3D9`/`NGL_GPU_ONLY` + `FX_ALLOW_INCLUDE` (fx), `RENDERINGDATA_ALLOW_INCLUDE`/`SCENEGRAPH_ALLOW_INCLUDE`, `USE_XAUDIO2` (audio), `XT_GAME` (xtgame), `LTM_DESC`/`LTC_SOURCE` (libtomcrypt, security), `ANIMATION_ALLOW_INCLUDE`, `LOGFS_ENABLE` + `CFILESYSTEM_CREATE_FUNC_ENABLED` (game, non-Profile/Master), `CREATE_CROWD_FLAG_RENDERER`. Per-file: `SPU_NET_TASK` on RacingPhysics `car.cpp`/`networkupdate.cpp`; `DEFLATE_MODULE`/`INFLATE_MODULE` on `PakCompressPacketZLib.cpp` (SPU-only builds; on PC the file is compiled once, plain).
- Link inputs on PC: `secur32 crypt32 ws2_32 dbghelp psapi`, DirectX SDK `dxerr d3d9 d3dx9 dinput8 dxguid xinput`, OpenAL 1.1 `OpenAL32`+`EFX-Util`, Demonware 2.0 (`bdConnection bdCore bdLobby bdSocket bdPlatform bdNet bdExampleCommonLobby ssleay32 libeay32 libcurl`, present in tree), Bink `binkw32`, Massive `xmassiveadclientlogging`. Flags `/SUBSYSTEM:WINDOWS /MACHINE:X86 /DEBUG /NODEFAULTLIB:LIBCMTD /NODEFAULTLIB:LIBCMT` (so the CRT is the DLL runtime). x86 only.
- Gaps the JSON reports: one stale PCH reference (`amax/library/Kanzen/jamfile.jam` names `StdAfx.cpp`; the files are `Kanzen_PCH.cpp/.h`); 18 missing include dirs, all explainable: `Amax$(_PLATFORM)` (empty on PC), `Code/Genesis/Library/include` (dead), `Advertising/IncludePath` (jamfile typo), `common/ai/air/include` (wrong path in one jamfile), and the vendor dirs Bink, Massive, OpenAL, `libs/vendor/jpeg/version62` (IJG libjpeg 6b, needed by `JpegHelper`). Library `Jpeg` is linked but has no jamfile in the tree.
- Generated headers: `CPFile x.cp|.cv|.sp` produces `x.h` next to the source with `#define CP_NAME n` + `#define CCP_NAME cn` (`.cp`, pixel constants), `CV_`/`CCV_` (`.cv`, vertex constants), `SP_`/`SSP_` (`.sp`, samplers; used as `register(SSP_...)`). Directives: `#set N` (counter), `#begin N` … `#end`, `#align N`, `#include "other.cp"` (chains parent module constants), `#skip`. `ImportCP header : TOP … Module` copies a generated header from another module into the current one. A reference output exists at `code/tools/spt_billboard/source/spt_billboard/shaders/{ps,vs}Constants.h`. 12 CPFile and 26 ImportCP records are in the JSON; the generator is T003 work.
- **`[ Batch files : StdAfx.h ]` was a unity build.** Each Batch group compiled as one translation unit: `SP_Rewards.cpp` calls a template that is only defined in `SP_SaveGame.cpp`, 190 files earlier in the same group, and hundreds of headers assume includes that an earlier file in their group provided. Nearly every library uses it (amax_gamelogic: groups of 10/2/6/195/7 files; gravity: 37 small groups). `gen_cmake.py` reproduces it with one generated `_work/build/gen/unity/<target>_batchN.cpp` per group (`--no-unity` compiles files individually, which needs many more include fixes).
- **`PLATFORM_PC` must be defined on the command line.** Every PCH header tests `#if defined(PLATFORM_PC)` for its Windows block (winsock2.h before windows.h, time.h) *before* it includes `core/Core.h`, the only place that derives it from `_WIN32`. Without the define the PCH skips winsock2 and the later `#include "stdafx.h"` in each source produces winsock/winsock2 redefinition errors. The original vcproj defined it; CMakeLists does too.
- Shaders: the jamfiles build `.fx` effects (`Effects`/`AmaxEffect` rules, 0 on PC in this extraction because the rule bodies are shader-farm specific) and `.psh`/`.vsh` objects (`OBJ_SHADERS`). Retail PC data already ships the compiled `.fxb` set, so M1 does not need the shader build.

## 2. Engine facts that constrain the port

### File system and paks
- Single global `Sys::I_FileSystem*`; in game it is `LogicalFs::C_OverlayFs`. Layers: 0 = loose cwd ("CFileSystem"), then paks mounted by `C_GameSystems::CreateFsLayers` (`amax/game/GameSystems.cpp` 201-265, `USE_NEW_PAK_LAYOUT`). Layer types `E_Type_Overlay` (first hit top-down), `E_Type_Opaque`, `E_Type_Newer`. In non-gold builds `Util.LogicalFs.OverlayFs.MasterDiscEmulation=false` makes every layer Newer, so a newer loose file overrides a pak copy.
- Choke point: `C_OverlayFs::GetBestLayer()` (`util/logicalFs/overlayfs/OverlayFs.cpp` ~488/571). Also `InsertLayer`/`AddLayer` for a new top layer. `Util.LogicalFs.OverlayFs.FileMappingDebug` logs every path-to-layer mapping.
- PC mounts: `cache/root.pak` at `/`, `cache/models.pak` at `/models/`, `cache/shaders-speed.pak` at `/graphics/shaders/speed/`, `cache/gamedata.pak` at `/gamedata/` (RSA-1024 signature `gamedata.sig`, key `g_amax_publicKey`, SHA-1 per file). Not mounted on PC: `root_streaming.pak`, `boot.pak`, `boot_rampak.pak`, `gamedata_boot.pak` (all inside `#ifndef PLATFORM_PC` in `BootLayer.cpp`). `lut_rampak.pak` is gated only by `g_enableLutRamPak`.
- Pak format (`util/logicalFs/pakfs/impl`): `PAK2` fourCC + version + sector size; `C_PakHeader` (SHA-1, codec, fat entry type, separator, meta string offset); XOR-obfuscated string table (key in `PakUtil.cpp`); FAT of `C_PakFatEntry` (32 bytes) or `C_PakFatEntrySecure` (+SHA-1), sorted by CRC. Codecs: Raw, ZLib, XMem, PacketZLib, PacketXMem. Hash: `C_PakCrc32`, poly 0xEDB88320, init 0xFFFFFFFF, no final XOR, over the normalised lowercase path with leading separator. Matches Blur2Test's `~crc32("\\" + path.lower())` on 29,913 of 29,913 records.
- I/O: PC `IoDevice.cpp` uses `CreateFile` with `FILE_FLAG_NO_BUFFERING` (sector-aligned reads). `C_LogFs` wrapper logs every access to `./user/logfs` in non-gold builds.
- **Pak version 2** (T005, 2026-09-23). The source reads version 1 only (`PAK_VERSION 1`); retail PC ships v2 for every pak except `shaders-speed.pak` (v1); Nov discs use v2 for `gamedata.pak` and v3 for `root.pak`. v2 layout, verified on all 7 retail PC paks: pre-header `PAK2`/version/sectorSize as v1; then U32 headerSize = 0x20 and a **packed** 32-byte header `{codec, fatEntryType, separator, unused, U32 codecFlags, U32 metaStrOffset, U64 fileTime, U32 stringTableBlockSize, U32 fatBlockSize, U32 unknown}` (no 20-byte integrity hash; the last word holds leftover characters such as `bin`, `ss`, meaning unknown). String table (U32 size + XOR-crypted names, padded to a sector) starts at **sector 1**, the FAT (U32 count + U32 bytes + entries) right after it, both block sizes sector-aligned as the header says. FAT entries are 40 bytes: the v1 32 bytes (crc, string offset, parent FAT offset in on-disk strides, logical length, U64 file time, U64 start sector) plus `U32 unknown` (per file; not the path CRC, not SHA-1 of stored or logical bytes) and `U32 storedSize`; secure entries append U32 padding + SHA-1 (64 bytes). Payloads have **no stored-size prefix** (v1 had one, not counting itself): ZLib streams start at the sector, PacketZLib starts with the U32 chunk cap 0x10000 then `[U32 size][data]` chunks, Raw is the bytes. The secure SHA-1 is over exactly `storedSize` bytes from the payload start. Retail codecs: root/boot/lut_rampak = PacketZLib (4), gamedata/gamedata_boot = ZLib (2) secure, root_streaming = Raw (1). The retail `gamedata.sig` verifies against the source's `g_amax_publicKey` when the SHA-1 is taken over the raw on-disk FAT bytes. The engine reader now handles v2 (`PAK_VERSION_READ_MAX 2`, `PakRead.cpp` `ReadFatV2`, codecs take the known stored size via `I_PakCompress::SetKnownPhysicalLength`); v3 is not implemented (not needed: Nov paks are extracted by Blur2Test).
- **Retail Xbox 360 Blur 1 paks (2026-09-24, hexdump of the disc under `C:\AIProjects\Blur\GameData\Xbox 360\`).** `cache/root.pak`: `PAK2` magic in big-endian byte order (bytes `50 41 4b 32`; the PC files read `32 4b 41 50`), version 1, sector size 0x800, then a U32 0x28 and the v1 `C_PakHeader` (20-byte SHA-1, codec 5 = `E_Codec_PacketXMem`, fat entry type 0, separator `\`). `shaders-speed.pak` is the same with codec 3 = `E_Codec_XMem`. So the retail 360 disc is pak v1, the version this snapshot reads natively, and the only two obstacles to reading it on PC are byte order (the reader copies structs in host order) and the XMem codecs: `misc_shared/Compression/XMemCompress.cpp` and `pakfs/impl/PakCompress*XMem.cpp` call the XDK `XMem*` API, which has no PC implementation in the tree, so a PC LZX decoder is needed (Blur2Test uses QuickBMS for this). The disc root also carries `default.xex`, `levels/` (showroom, spa_barcelona_oval, uk_brighton, usa_amboy, usa_la_downtown, usa_la_longbeachdocks, usa_la_river), `boot.pak`, `boot_rampak.pak`, `gamedata_boot.pak`, `lut_rampak.pak`, `root_streaming.pak`. Detection of all this is `GameSource::Detect` in `Blur1Multi/code/mercury/library/util/gamesource/`.
- **XMem LZX on PC (T071, 2026-09-24).** Blur1Multi reads Xbox 360 paks through the engine's own pak code with a PC implementation of the XDK xcompress API (`Blur1Multi/code/vendor/xmem-pc`, over libmspack 1.11 `lzxd.c`, LGPL 2.1). Facts established on the way, each checked against Blur2Test's QuickBMS extraction:
  - *Pak reader.* `PakRead.cpp` already byte-swaps big-endian paks (pre-header, `C_PakHeader`, FAT via `BinaryDeserialiserAutoEndian`); the only missing pieces on PC were the XMem codecs. `PakEntryFile.cpp` selects `C_PakCompressXMem`/`C_PakCompressPacketXMem` only under `PLATFORM_XENON || CFG_CONVERTER`, and `misc_shared` compiles `Compression::XMemDecompress` only with `USE_XMEM_COMPRESSION`, which its jamfile defines for Xenon and for PC tool builds, where it links the XDK's Win32 `Xcompress.lib`.
  - *Frame chain.* An XMem LZX stream is a chain of frames `[u16 BE compressed][data]` (32 KB out) or `[FF][u16 BE out][u16 BE compressed][data]`; a zero compressed size ends it (the stream writer emits five zero bytes). The LZX state carries across frames; each frame's data starts a fresh bit reader. Window 128 KB (17 bits) and no reset interval decode everything on both discs. The E8 header bit is read once per stream.
  - *No pad byte after an odd-sized uncompressed block.* CAB-style LZX (libmspack's default) skips one byte after an uncompressed block of odd length; XMem does not: the next block header starts on the byte right after the data. Found on `models/vehicles/foose_stallion_stock.model` (Aug 31 `models.pak`: uncompressed block of 66,791 bytes, next frame 6,903 + 16 + 25,865 = 32,784 compressed bytes). `lzxd.c` has this under `BLUR_XMEM_LZX`.
  - *Packet codec (5).* `[u32 stored][u32 packet 0x10000][chunks]`, chunk `[u32 compressed][XMem frame chain]`, `0xFFFFFFFF` = stored raw. A logical size that is an exact multiple of 64 KB is followed by an empty chunk (`compressed` = 0) that the writer flushed.
  - *Secure paks.* `gamedata.pak`/`gamedata_boot.pak` on the retail 360 and Aug 31 discs are signed with the same `g_amax_publicKey` as retail PC (RSA-1024, PSS, SHA-1, salt 8, libtomcrypt `rsa_verify_hash`); the signature covers the SHA-1 of the FAT **as stored on disk** (big-endian), which was the Xenon build's host order. The PC reader hashed its byte-swapped copy, so the check failed ("Hash doesn't match", fatal only in `CFG_GOLD`); the Blur1Multi overlay of `PakRead.cpp` keeps the on-disk FAT for the hash. Checked with `Blur1Multi/code/tools/xmem-verify/sigcheck.py` (4 of 4 signatures verify over the on-disk FAT, 0 of 4 over the swapped one).
  - *Mount set.* For an Xbox 360 source, `CreateFsLayers` (Blur1Multi overlay) mounts the Xenon list: `root.pak` and `root_streaming.pak` at `/` (the latter with the 128 KB XMA buffer), `shaders-speed.pak` at `/graphics/shaders/speed/`, secure `gamedata.pak` at `/gamedata/`, then `gamedata_boot.pak` as a RAM pak at `/`. `boot.pak`, `boot_rampak.pak` and `lut_rampak.pak` are mounted later by `C_BootLayer` under `#ifndef PLATFORM_PC` (T072 needs them). There is no `models.pak` on the retail 360 disc (models are in `root.pak`); the Aug 31 disc has one, which the Xenon list never mounts.
  - *Disc root marker.* The prototypes' title executable is not `default.xex` (Aug 31: `Kanzen_Speed.xex`); `GameSource::Detect` accepts any `.xex`.
  - *Verified.* Standalone (`Blur1Multi/code/tools/xmem-verify/xmem_verify.cpp`): all 10 Aug 31 archives, 8,385 files, byte-identical to Blur2Test's full extraction, XMem stream files also through `XMemDecompressStream` in 777-byte pieces; all 8 retail 360 archives, 5,842 files, decode to their FAT lengths, and the 49 with a Blur2Test reference are identical. In engine (`BLUR1MULTI_PAKDUMP`, `pakdump_compare.py`): 1,661 files (723 MB) read through the mounted Aug 31 paks and 49 through the retail disc, all identical, no signature errors.
- **Xbox 360 -> PC conversion (T072, 2026-09-24).** Blur1Multi converts a 360 source's assets when they are opened (`Blur1Multi/code/mercury/library/util/x360convert`: engine-independent converters; `engine/X360ConvertFs.cpp`: an `I_FileSystem` wrapper installed with `SetFileSystems` for 360 sources). Each converter is written from the engine's PC reader and the tool-side writer, and checked with `code/tools/x360convert-verify` against the retail PC file of the same asset (retail 360 and retail PC are the same game, so 385 textures, 2 fonts, 2 particle meshes and 73 flasks exist on both).
  - *What differs by type* (`code/tools/xmem-verify/survey.py` over every retail pak): same size and leading bytes on both platforms: `.csv .dds .ipf .aid .pf .raw .wbl .txt` (pass-through candidates, not yet checked byte for byte); same size, swapped magic: `.cycle .skeleton .dat .xt .bin`; different sizes: `.model .texture .loc .bpr .font .fxb .baf`. The retail 360 disc keeps levels loose (`levels/<track>/level.*`).
  - *`.texture`.* `Texture{Header{U32 version, U32 flags}, Data}`. PC `Data` = `TextureDesc{Width, Height, Depth, Levels, Format (D3DFORMAT), Usage, Type 3/5}` + tight levels (cube face-major); 360 `Data` = 52-byte Xenon `D3DBaseTexture` (fetch constant at +0x1c) + size, alignment, unused + tiled allocation. Conversion = endian mode, untile, Xenos format -> D3DFORMAT (`0x12` DXT1, `0x13` DXT3, `0x14` DXT5, `0x06` -> 21 A8R8G8B8, `0x02` -> 28 A8, channel order unchanged); the untiling and mip layout are Blur2Test's `b2_extract_textures.py` ported to C++. Retail PC `Usage` holds uninitialised bytes (`0x78138ced` in many files); the PC loader ignores it, the converter writes 0. Result: 382 of 385 identical to retail PC; the 3 others (`dontship/textures/debugframe`, `background`, DXT3) are the same images DXT-encoded separately per platform (decoded colours within 3 and 9 of 255).
  - *`.font`.* `Font{Header{U16, U16}, Data{U16 count, count x (U16 unicode, U16 page, 7 x F32)}, Texture{U16 pages, pages as texture Data payloads}}` (`Font.cpp` `C_FontResource::Load`). 2 of 2 identical.
  - *`.particlemesh`.* `PtlData{U32 version, UsrVar3{U32 variants; name (U32 length + bytes), U32 vertices, F32 scale, U32 shapes, shapes x vertices x 14 F32}}`, written with `BinarySerialiserAutoEndian`. 2 of 2 identical.
  - *XT flasks (`.bin`, `.xt`, tag `FLSK` big-endian / `KSLF` on PC).* The exporter (`xt2/source/tool/Export/XtFlaskExport.cpp`, `XtFlaskSwizzle.cpp`) swaps every table entry at its width and record data through the schema (atoms, enums, flags 4 bytes, 64-bit atoms 8, pointer 2 x U16, handle U32, array U16+U16+U32; each component's bytes padded to 4); the schema string pool and record strings are a byte cipher (`XtFlaskDecodeStrings`) with no byte order. The same walk run with the file's own tables converts back. 54 of 73 identical to PC; `code/tools/xmem-verify/flaskcmp.py` shows the rest differ in content, not layout: the PC build's schema has more fields (`AmaxVehicle` 620 bytes on PC, 612 on 360, `AudioEngineType` among the additions), PC-only UI records, different audio entity sets. Where records, components and data are the same, the only difference is that stub type size.
  - *`.bpr` resource bundles (BZR2 v3).* `C_BundleHeader` (platform byte 1 Xbox 360, 2 PC), a system-memory block (chain of 28-byte `C_ResourceTexture2D` headers, then the string table) and the texel block; the headers are the same structs byte-swapped. 360 texels come from `tools/ResourceBundler/source/export_resource/360/ExportArrayOfTextures2D360.cpp`: `XGSetTextureHeaderEx` with defaults (no stored fetch constant: pitch rounded up to 32 blocks, packed mip tail even for a lone base level of 16 texels or less, mips after the base slice), A8R8G8B8 4-byte reversed by the exporter, DXT blocks 8-in-16 swapped (the exporter's swap skips DXT, so it happens in the tiling step; established by comparison), L8 unswapped. PC texels are tight, resources back to back. Result against retail PC (`code/tools/xmem-verify/bprcmp.py`): 281 of 296 resources identical; 14 differ only in length, because the retail PC bundler gave mip levels smaller than one DXT block 0 bytes while the PC loader (`Display2::GetTexture2DSize`, blocks rounded up) reads a full block, so retail PC reads 8 or 16 bytes past such a resource (the converter follows the loader's rule); 1 differs in content (`xbox360_buttons`, controller glyphs on 360). The per-resource flags word is constant per bundle, unrelated between platforms (`0x251`/0, 465/18, 725/725) and unread by the PC loader; written as 0. With bundles converted the front end draws its menu cards and sky from the 360 disc.
  - *`.loc` localisation (tag `XTLO` on 360, `OLTX` on PC).* Writer `xt2/source/tool/Export/XtLocExport.cpp`: header, table of contents, 24-byte language entries (name[16] + offset/size), a lookup block of 8-bit string ids, then per language a table, (id, offset) entries and UTF-16 strings, every U32 and UTF-16 unit swapped. Converted against retail PC (`code/tools/xmem-verify/loclist.py`): every string present in both files is identical in all five shared languages (en, fr, de, it, es); the 360 files add ja, pl and ru, and PC files add PC-only strings (125 in `common.loc`), so no file is byte-identical. With it the front end shows its text and the Xbox button prompts.
  - *`.cycle` and `.skeleton` (engine-reader converters).* Both are plain serialised streams read with `Sys::BinaryDeserialiser` by `C_Cycle::Deserialise` / `C_Skeleton::Deserialise` (`animation/include/animation/{cycle/CycleDeserialise.inl,skeleton/SkeletonDeserialise.inl}`). `x360convert/engine/EngineConverters.cpp` runs those exact readers over a transcoding stream that mirrors `BinaryDeserialiser`'s dispatch (the eleven scalar `>>` overloads, `Read` for raw bytes, everything else through `Sys::Deserialise`): each scalar is taken big-endian and written little-endian, so the output is what the PC reader consumes. First attempt used one generic `>>` and swallowed `C_JointTransform` as a 48-byte SIMD blob (40 bytes on disk), overrunning by 16 bytes; the scalar set fixes it. Checked with `BLUR1MULTI_PAKDUMP` through the converting file system (`code/tools/xmem-verify/pathlist.py`): cycles 801 of 803 identical to retail PC (the 2 others: two light names numbered the other way round and matching key values 0/1.0 swapped, authored content), skeletons 20 of 20.
  - *`.model` (T072, 2026-09-25).* `[FourCC] Model{Header, MdlDat, Render{Render{Header, Scene}}, Coll}` then `MtaDbg` (`C_ModelResource::LoadModelData`; the model's Render block holds the Render block `C_RenderModel::Read` opens). 50 older models (same 50 on PC) have no FourCC and start with `Model`. `Header` blocks are one U32. Converter: `x360convert/engine/EngineConverters.cpp` `ConvertModel`. Results over all 1,544 retail 360 models through the engine (`BLUR1MULTI_PAKDUMP`, `code/tools/xmem-verify/modelcmp.py`): 1,544 convert; against the 1,542 with a PC counterpart, MdlDat 1,541 identical (the other is different content, 1,348 vs 608 bytes), Coll 881 identical (vehicles 141 of 141; the rest differ in 1 to 4 words of content, e.g. a float the 360 export has where PC has 0), Render 171 identical (why the rest cannot be, below).
    - *MdlDat* (`C_ModelData::Read`): child blocks Header/Models/Element/Constr are 32-bit words only (S32, F32 matrices and bounds); StrTab is `Util::C_StringTable` = `Ut::Vector<U32>` offsets then `Ut::Vector<char>`, each with a U32 count; characters stay as they are.

    - *Render/Scene* is the rendering-data archive (`Arch::BinaryInputArchive`). The 360 file was written by the PC-hosted exporter with swapping on: header `ARCH, 1, 0xffffffff` (PC `ARCH, 1, 0`), every object tagged `'AR'` + U16 version, `PlatformType` 0 (360) where PC has 2. `x360convert/engine/SceneTranscode.{h,cpp}` runs the engine's own reader (`RenderingData::Target::Deserialise(Scene)`, `(ResourceBlock)`, instantiated for `Arch::X360SceneTranscoder` by `SceneTranscodeInstantiate.inl`, included at the end of the Blur1Multi overlay copy of `renderingdata/source/noninterface/target/archive.cpp`) over an archive that takes each scalar big-endian and writes it little-endian. Non-template overloads replace the payload readers so nothing reaches the device. The exporter rules they follow (`renderingdata/source/noninterface/build`):
      - Buffers are `Arch::Serialiser` blocks: 360 XMEM_COMPRESSION when the payload is 128 bytes or more (fragments of 32 KB, each an XMem frame stream), PC NO_COMPRESSION with endian flag 0; alignment 16 on both, relative to the start of the Scene payload.
      - Vertices go through the swapping serialiser element by element at their own width (S16/F16 pairs and quads per 16 bits, F32 per 32 bits, U8_4/U8_4N/SHHD_3N/SDDD_3N as one U32).
      - Normals: `Scene::Finish(PC)` first runs `ChangeVertexElementType(SHHD_3N, U8_4N)`, so PC's U8_4N normal is `VertexData::ChangeDataType` of the SHHD_3N value (11/11/10 signed fields /1023, /1023, /511; `(v + 1) * 0.5` clamped, `int(v * 255)`, W = 0). The converter does the same and remaps the element type in every VertexFormat and VertexDeclaration.
      - Indices: `Scene::BuildStrips` strips each index buffer lod with the ATG stripper; 360 and PS3 pass `ATGTRISTRIPPER_USE_RESET_INDEX`, which runs the stitched strip through `ConvertDegensToResetIndex` (restart 0xffff; a strip that sat at an odd position comes out with its first index doubled if even-length, reversed if odd-length). PC keeps the stitched strip. The converter splits each draw range at the restarts and stitches as `CStripper` does (`last, first` between strips unless equal, one more `first` when the parity is wrong). A doubled start is a counter-clockwise strip; an odd-length strip is stitched as clockwise at an even position, which draws the same triangles if it was reversed. Draw ranges (`Primitive::Lod` offset/count) are read before the buffers they index (Scene before resource blocks), so the reader runs twice: pass 1 collects every range and its buffer (`RenderListNode::GetIndexBufferSource` of the primitive's list index, resolved by the node streamer when the node is complete), pass 2 converts and the ranges are patched at the end. Every range is checked: the re-stitched strip must draw exactly the 360 range's triangles with their winding; all pass.
      - Textures: shared textures are `Writer<Texture>` (the NglXeTex / NglPcTex HEADER_AND_DATA blob behind a byte count, converted like a `.texture` Data payload); resource-block textures are `LodWriter<Texture>` per lod: the 64-byte Xenon header of the texture from that lod's top level down, then the data of its first levels in an `Arch::Serialiser` block. `LodCalculator::GetMipLevelsForLod`: lod 0 writes every level of that header, any later lod one level. The data is NglXeTex's `sizeUsed`: the XG allocation less 4 KB (DXT1) or 8 KB (DXT5) when the chain reaches the packed tail and the texture is less than four times taller than wide. Xenos 8_8 (0x0A) is PC D3DFMT_A8L8 (51) (`uv_distort*` in 169 models).
      - PC `TextureDesc.Usage` holds uninitialised bytes (text fragments in the retail files), so any Render with a texture differs from PC in those four bytes.
      - Why most Render blocks cannot match PC byte for byte: `Scene::Finish` changes the normals (PC only) before `ShareVertices`, `BuildLods` and `BuildStrips`, which order and simplify by vertex bytes. PC and 360 exports of the same model therefore have different vertex orders, strips and lower-lod meshes (in 1,121 of the 1,542 models at least one vertex buffer differs from PC in content or order). The converter reproduces the 360 geometry exactly (triangle check above); what it cannot reproduce is PC's separate export.

- **Frame rate: 60 Hz simulation, uncapped interpolated rendering (2026-09-24).** The timer floor was 1/60 s, so above 60 fps the game ran fps/60 times fast; the floor is now 1 ms. The simulation cannot take shorter steps: `RacingPhysics::Car` integrates a hard-coded 1/60 s per step (`car.cpp`, `CreateGravityCache` sets `m_dd.frameTime = 1/60`), and much per-frame game logic (vehicle `FakePhysics` forces added per frame, pickup/decoy/reverse-nitro rotations, input auto-repeat, light trails) assumed one frame per step, as the Aib0t write-up found. So the PC loop (`C_Application::IdleLoop`, ApplicationPC.cpp) now decouples update from render: the game update runs only when 1/60 s of real time has accrued, consuming whole ticks (max 4) and reporting exactly that time to the game through the timer's forced frame time (`g_Blur2PCForcedFrameTime`), so every update runs whole 60 Hz steps; every loop iteration renders. Rendered frames between updates blend poses: `WorldRender::C_ModelInstance::SetElementMatrix` records each element matrix's previous-tick and current-tick values; before a render the ones that moved on the latest tick are written as a blend (quaternion slerp, linear position and scale; jumps over 20 m are not blended) and restored after it. The camera uses its existing motion-blur interpolation (`C_Camera` previous pose, `I_Feed::ToViewSetup`) shifted by the render fraction, only for cameras updated on the latest tick. Cost: up to one tick (16.7 ms) of display latency. Measured: 144 fps render, 60 Hz update, camera advancing 0.33 m on every rendered frame at speed (previously repeated positions). `BLUR2PC_DECOUPLE=0` restores one update per rendered frame; `Framework.Timer.FrameLimit` / `BLUR2PC_FRAMELIMIT` caps rendered fps (default 0, uncapped). #### PS3 SHHD_3N vertex elements: converted to F16_4

Source paths are relative to `Blur1PC/code/mercury/library/` unless they start with `Blur1Multi/`.

**Why.** The PS3 effects are RSX vertex programs translated to HLSL. They read SHHD_3N as the RSX
fetches it: `CELL_GCM_VERTEX_CMP` (`graphics/display/source/device/gcm/GCMDevice.cpp:2966-2977`;
`graphics/fx/include/fx/targets/cell/gcm.h:109,118` gives CMP the same value as
`CELL_GCM_VERTEX_S11_11_10_NR`, i.e. signed and normalised, 11:11:10). The Xbox 360 path repacks
SHHD_3N as PC's U8_4N (n*0.5+0.5, w byte 0), which is what the PC effects expect but not what the
translated PS3 programs expect. A decode in the shader does not work because the same semantic
changes type between declarations: NORMAL and TEXCOORD2 are always SHHD_3N, while TEXCOORD1 and
TEXCOORD3 are mixed (TEXCOORD3 is SHHD_3N on vehicles and perks and U8_4 bone indices on skinned
characters). Every SHHD_3N element is therefore converted to **F16_4 (x, y, z, 1)**: for PS3
sources first, and for Xbox 360 sources as well since 2026-09-25 (see "Xbox 360 sources: SHHD_3N and
the damage volume" below). The 360 rows of the verification table were taken while the change was
PS3-only.

**Scaling.** x / 1023, y / 1023, z / 511, w = 1. The source supports this:
- `DataTypes::SHHD_3N` (`graphics/renderingdata/include/renderingdata/datatypes.h:333-367`) packs x:11,
  y:11, z:10 from bit 0.
- The exporter encodes x * 1023, y * 1023, z * 511 (datatypes.h:340-343, 349-351) and decodes with the
  same divisors (datatypes.h:345-347).
- The PC exporter's own SHHD_3N -> U8_4N conversion goes through that decode
  (`graphics/renderingdata/source/noninterface/vertexbuffer.cpp` ChangeDataType).

The exact RSX CMP normalisation is **not documented in the tree**: the gcm headers carry only the enum
names, and no Sony GCM documentation is available here. For reference only: RPCS3's vertex fetch
(`rpcs3/Emu/RSX/Program/GLSLSnippets/RSXProg/RSXVertexFetch.glsl`, `fetch_attribute`, COMP32 branch)
shifts each field into 16 bits and divides by 32767. That gives x*32/32767 (about x/1023.97) and
z*64/32767 (about z/511.98), with w = 1. Against x/1023 the difference is under 0.1%, about 2 F16
ulps. RPCS3 is an emulator, so this is a cross-check, not ground truth. The w = 1 value is the same in
both. -1024 (x, y) and -512 (z) decode to slightly below -1 and are not clamped; 11 components across
all 1540 PS3 models hit those values, and none in the levels.

**What moves** (`Blur1Multi/code/mercury/library/util/x360convert/engine/SceneTranscode.{h,cpp}`,
`SceneTranscodeInstantiate.inl`):
- **Element type:** SHHD_3N is written as F16_4 in both vertex formats and vertex declarations (the
  `VertexElementType` overload).
- **Vertex data:** each SHHD_3N grows from 4 to 8 bytes. Every later byte of the vertex, padding
  included, moves by 4 per earlier SHHD_3N element. The VertexFormat DataSize (stride) and Offsets
  (`noninterface/archive.inl:246-252`) are rewritten, and so are the Arch::Serialiser block sizes,
  since the blocks are rewritten uncompressed.
- **VertexDeclaration element offsets** (`archive.inl:256-277`): +4 for every SHHD_3N element before
  them in the same stream.
- **`PrimitiveStream::vertexOffset`** is a byte offset into its vertex buffer. The exporter sets it as
  `offset * vertexSize` (`build/resourceblockbuild.cpp:409`), so it is rescaled from the old stride to
  the new one. The buffer is found through the node's VertexBufferSource, which the node reads after
  its primitives. The two-pass machinery from the strip re-stitching handles this: layouts are
  collected in pass 1 over the scene and every levelstream chunk, and offsets are patched in pass 2
  (PatchStreams, called from PatchLods).
- **Declaration check:** every primitive's declaration is checked against its buffer's layout. Each
  element of that stream must exist in the buffer with the same type and the same new offset.
- **Level stream layout:** C_LevelConversion takes its layout from the pass-2 output sizes, so its
  chunk offsets and sizes follow the wider vertices with no further change.
- **Two kinds of stream have nothing to move:**
  - Streams whose VertexBufferSource is (-1,-1) take a buffer supplied at run time;
    `target/render.cpp:335-347` leaves the slot empty. The conversion fails if such a stream's
    declaration would change.
  - Streams whose resource block the file never holds: no ChunkInfo item names the block and the scene
    does not carry it. The engine never gets a buffer for them (`target/render.cpp:335-376`) and skips
    the primitive (`target/context.cpp:486-496`).

**Built-in PC shaders.** None of them read model or level vertex buffers:
- All 85 `.vsh` files were checked. The ones with NORMAL/TANGENT/BINORMAL inputs (vsMesh, vsMinimal,
  vsCloth, vsParticle, vsAuxFlares, vsCrowdFlag, vsLightTrails, the UI polygon shaders, vsSkinnedMesh,
  vsSPTRender) are fed by their own dynamic or mesh buffers, or belong to tools and samples.
- The built-in passes that draw scene-like geometry (drop shadows, blob and collision-mesh shadows,
  mask, occlusion) read POSITION only.
- Scene primitives always draw with their scene effect (`Effect::OnLoad`).
- No runtime CPU code reads scene vertex-buffer contents or strides apart from the renderer's
  `vertexSize`, which comes from the rewritten DataSize.

**Verified** with a scratch harness that links the engine libraries and runs the engine converters
outside the game (`scratchpad/vtx/scenetest.cpp`, `build.bat`):

#### PS3 vehicle bodies: the damage stream (stream 3)

288 of the 306 PS3 `veh_*` effects have no POSITION input: their vertex input declaration lists TANGENT 0 and BINORMAL 0 on stream 3 (annotation `stream` 3, F16_4). The translated programs take the body's position from TANGENT and its normal from BINORMAL; only `veh_alloy*` (rims) and `veh_shadow*` (18 effects) read POSITION. No other PS3 effect uses a stream the engine generates at run time: across the 820 effects, the only `stream` annotations are these. The level vertex colours (`instancemode instance`) come from the level files.
- *PS3 build.* `C_VehicleModel` creates the stream under `PLATFORM_PS3` (`vehicle/source/VehicleModel.cpp:255-351`): one dynamic primitive stream per body primitive (`streamIndex` 3, `vertexOffset = (offset / stride) << 4`) and one buffer per body vertex buffer, 16 bytes per vertex, initialised to x = y = z = 0.0 and the U32 0x80000000. It destroys them at :478-486. The platform-neutral render path binds the stream (`scenegraph/source/Context.cpp:564-567`, `renderingdata/source/noninterface/target/context.cpp:303-310, 513-524`). The SPU job `SpuDamage::DamageTask` (`vehicle/source/damage/SPU/SPUDamageJob.cpp:642-801`) fills it. For each vertex it reads the position (F16_4, +0) and normal (SHHD_3N, +8) of stream 0, the morph offsets (TEXCOORD2/3, SHHD_3N), the control-point bytes (TEXCOORD4) and the colour's first byte. It adds the damage lattice (trilinear over 3 layers of 8x8 nodes), the control-point blend and the morph targets scaled by the deform level. It writes position.xyz with w = 2 x scratch, and normal.xyz with w = min(0.996, deform) + rear-light attenuation, as 8 F16 halves. `C_DamageLayer` kicks the job (`InitSPUDamage` `DamageLayer.cpp:149-262`, from `VehicleActor.cpp:6374-6376`; `FinaliseSPUDamageJob` :775-812) when `forceRun` is set. That happens at creation, in `SetUpdateInfoTexture` (:467), `ProcessDeformEvents` (:766), `Repair` (:2586), `RestoreDamageState` (:3497) and every frame while `m_UpdateVolumeTexture` is set (`UpdateDamageTextures` :688-692, which the PS3 never clears once set). `C_ContextManager::FinaliseContext` runs at most one job per frame (`m_MaxPerFrame = 1`, `SPUDamageContext.cpp:11, 56-65`; the count is zeroed at the start of `C_GameWorld::Update`, `GameWorld.cpp:2205-2207`). The PC build creates no stream 3 and deforms in the vertex shader, so for a PS3 source the body drew from an unbound stream and was invisible.
- *Port* (`Blur1Multi/code/mercury/library/graphics/vehicle/source/damage/Ps3DamageStream.{h,cpp}`; overlay copies of `VehicleModel.cpp` and `damage/DamageLayer.cpp`, each PS3 branch mirrored under `GameSource::Current().m_Platform == E_Platform_PS3`). The stream-3 buffers and dynamic streams are created and destroyed as on the PS3. The body buffer bytes are read once when the stream is created (managed pool). The damage context is kept per layer; the five `forceRun` triggers, the `UpdateDamageTextures` branch and `ForceDamageContextToRun` are mirrored, as are `FinaliseSPUDamageJob` (including "if (!forceRun) SetUpdateVolumeTexture(false)") and the one-job-per-frame limit. A frame starts when a layer that already updated since the last start updates again, which matches the PS3 when every layer updates once per game-world update. `InitSPUDamage` runs on the layer's first `Update`: `C_VehicleModel::Initialise` has by then set the extents, built the height profile and filled the control points (`VehicleModel.cpp:220-224, :357`), and every vehicle model is created by `C_VehicleActor` (`VehicleActor.cpp:5493`). The job runs synchronously, reading the lattice as it is; the PS3's lattice double buffer (`SwapBuffers`) served only to give the SPU a stable copy.
- *Job port* (`Ps3DamageJob::Run`): the vertex loop step by step, with scalar versions of the SPU-only helpers:
  - `load_unaligned_float16_4`: the SPU's bit trick, not IEEE; half denormals and infinities decode as it did.
  - `load_unaligned_SSHD_3N`: (word << {21, 10, 0}) & masks, / 2^31, one fused multiply-add with the listed scale and bias.
  - `float32_to_float16` (Edge): truncation; below 2^-15 flushed to 0 without its sign; 2^16 and above clamped to 0x7BFF.
  - `saturate`: through unsigned 0.32 fixed point, so 1.0 becomes 0.99999994.
  - The SPU's single-precision rounding (towards zero, denormals flushed) is set for the duration of the job.
  - Input comes from the converted declaration: F16_4 position and normal wherever the declaration puts them. The model converter writes SHHD_3N as F16_4 (x/1023, y/1023, z/511, 1); the job recovers the SHHD_3N word by rounding each component (exact: consecutive values are more than two F16 steps apart) and decodes it as the SPU did.
  - Output is little-endian F16.
  - Not reproduced: the SPU's saturation in place of infinities and NaNs, and the rsqrt-estimate `Normalised()` (here 1/sqrtf).
- *Verification* (offline harness on 12 PS3 vehicle models converted by the engine converters, 165,879 body vertices in 67 buffers):
  - Every SHHD_3N word (497,637) is recovered exactly from the converted F16_4.
  - With a zero lattice and zero control points, the job's position halves equal stream 0's and w = 0 for 164,088 vertices. The other 1,791 components are halves below 2^-14, which the job's F16 store writes as 0 (as on the PS3).
  - A Python transcription of the SPU source (float64 arithmetic; single precision rounded towards zero where a lattice cell index depends on it) agrees with the port to at most 1 F16 unit in the last place: 22 of 1,327,032 output halves undamaged, 257 of 1,327,032 with a random lattice and control points.
- *Unknown*: the SPU `Normalised()` and estimate-based results bit for bit. The byte the SPU read when a buffer has no colour element (`addr[UINT_MAX]`, the byte before the vertex in local store; here 0). Control-point indices past the 18 fetched (here entry 0). None of these three cases occurs in the vehicle data checked.

#### PS3 effects

The PS3 exporter (`fx/source/targets/ps3fx.cpp`, `NglPs3Fx::IsBigEndian`) writes the same `FX::Effect` graph as PC and 360 (version 9), big-endian, in a `PS3FX` block; all 820 retail PS3 effects parse to their last byte with the 360 converter's graph reader. Against the retail PC effects of the same name: names, structs and pass annotations are identical (820); parameters and parameter data identical in 516 (the PS3 sets the sampler sRGB bit as PC does, `SamplerStates.cpp:25`); vertex input semantics identical in 507 and already in the PC numbering (no usage shift); technique lists identical in 312 (PS3 adds `MaterialAlphaLuminance`, `...Lights`, `...LOD`; it has no `*NoDamage` or, in 304 effects, `MaterialPrepass`); render states identical in every one of the 3,359 techniques present on both sides once word 14, `ColorWriteEnable`, is mapped from the GCM colour mask (A bit 24, R bit 16, G bit 8, B bit 0; `ngl/ps3/ngl_ps3_gpu_types.h:629-634`) to D3D. No PS3 vertex program samples a texture (PC has 864 passes with a vertex sampler: vehicle damage).
- *Programs* are CGB blobs (`sce-cgc -mcgb`, `ps3fx.cpp:300-343`); the SDK header is not in the tree. Layout (measured; all 7,574 program instances parse to their last byte): `"CGB\0"`, U32 0, U16 ucode size, U8 kind (0 vertex, 1 fragment), U8 3, 16-byte configuration (VP: U16 attribute input mask, U8 temp count?, U32 attribute output mask; FP: U32 attribute input mask, U16 texCoordsInputMask, U16 texCoords2D, U16 centroid, U32 fragmentControl), U32 (FP: register count in the top byte?), ucode at 0x20, a constant table (U16 block size, U16 n, U16 registers, float4 values; VP literals uploaded per draw, `GCMFunctions.inl:1004-1016`; empty in every FP), and a parameter map (entries {type, name, parent, resource}; FP uniforms point into a U16 table of {register, n, byte offsets of the n embedded copies}). RSX fragment programs have no constant registers: uniforms are float4 literals embedded after the instruction that reads them, patched per draw by name (`fx/source/System.cpp:233-278`, `FxContext.cpp:542-640`); all 39,988 listed offsets land on such literal slots. Full field tables: `Blur1Multi/code/mercury/library/util/x360convert/source/RsxTranslate.h`.
- *Converter* (`x360convert/source/Ps3EffectConvert.cpp`, `RsxTranslate.cpp`, written from the NV40/RSX layouts; RPCS3 and Mesa nouveau used as references only): each program is translated to HLSL and compiled with `D3DCompile` for vs_3_0 / ps_3_0; bindings are rebuilt: vertex parameters that sce-cgc placed at c256-c467 (unregistered parameters are allocated downward from c467) move to the lowest free registers (333 bindings), CGB constant-table literals become HLSL literals; fragment bindings (per struct member on the PS3, `Offset` in floats, 2,370 without a listed register) become one binding per parameter with `Offset` 0 (the PC loader asserts it, `System.cpp:210`), at the listed register when it fits c0-c223, else allocated (2,370); every embedded copy the map lists for a bound member reads `C[register]` (40,726 of 67,414 fragment literals), the rest stay literals as they did on the PS3.
- *Sampler dimension.* A fetch names only a texture unit and the effect records no sampler type. From the programs alone, of 3,613 effect/sampler pairs 246 are proven to read at most 2 coordinates, 808 read 2 by swizzle pattern and 2,369 are undetermined. Rule chosen by the user (2026-09-25): a sampler is a cube when its packed AddressW (bits 6-8 of the sampler-state word, `Fx_export.cpp:512-527`) is non-zero, 2D otherwise. It rests on how the retail effects were authored: in the source snapshot AddressW is set in exactly three sampler declarations, all cube (`amax/game/Shaders/Common/Lighting.h:66-78` `g_tEnvironment`; `graphics/vehicle/include/vehicle/shaders/vehicle_common.h:594-617` `g_sVehicleEnvironmentTexture`, `g_sLightEnvironmentTexture`), and in the 820 PS3 effects AddressW is non-zero for exactly those three names (780, 960 and 560 bindings) and zero for all other sampler bindings. No PS3 fragment program samples a volume texture.
- *Semantics taken* (sources in `RsxTranslate.cpp`): DIVSQ = a / sqrt(|b|) and 0 where a is 0; RSQ uses |x|; COL0/COL1 inputs clamped to [0, 1]; texCoords2D-flagged coordinates read z = 0, w = position w; src2 bit 31 ("disable perspective-correct interpolation", Mesa; RPCS3 multiplies by 1/w) reads the input divided by w (4,228 reads, all under NRM/DIV/DP4/DIVSQ); for these every translated vertex program also writes its position w to TEXCOORD9. Condition codes (2 registers, per-component conditional writes, KIL = discard if any), source precision clamps, destination scale, saturate, VP dual issue (both halves read before either writes), VP relative constant addressing (skinning) and VP BRI (forward, 2 programs: `cs_eye_skin_ln`, `_nv`) are translated. Half-precision (H) registers are translated as float. H(2n) and H(2n+1) alias R(n).xy / R(n).zw; the translator keeps them as separate variables and proves per component read that no read crosses views (none does once `MOV Rn.m, Rn.m` self-copies are dropped: they copy the same bits). FP output: R0 (fragment control 0x40, every program) to COLOR0; R2-R4 to COLOR1-3 only as a contiguous prefix and only when the register's final content came through the R view (GCM render-target sets are contiguous, D3D9 requires contiguous outputs).
- *Verification* (`code/tools/ps3shader-verify`, `_work/tools/build_ps3shader_verify.bat`): all 820 effects convert, 7,574 programs translate and compile (112,802 vertex and 157,846 fragment instructions; 9,553 2D and 2,300 cube sampler bindings; 410 KIL, 16 vertex branches). `code/tools/xmem-verify/fxbcmp.py <converted> <pc> --by-technique`: of the 3,359 techniques on both sides, pass names and render states match in all; bound parameter sets match PC in 2,223 (vertex) and 2,415 (fragment) — the differences are PC-only `g_vHalfPixelOffset` (666 fragment programs), PC-only vehicle damage bindings (vertex textures, `g_vCodeDamageScale`, `g_vControlPoints`), PS3-only `g_vNearFar`/`g_tAlbedo` in some passes; registers and counts differ where fxc and sce-cgc allocated differently. - *Differences the engine will meet* (not converter faults): (1) the PS3 prepass writes one target, normal.xy * 0.5 + 0.5 and view depth packed into z/w as two 8-bit fractions (`advert_ln` MaterialPrepass: `floor(z * 255) / 255`, `frac(z * 255)`), where the PC prepass writes normal.xyz to oC0 and z/w to oC1: PC deferred consumers will misread a PS3-effect G-buffer; (2) no PS3 program uses `g_vHalfPixelOffset`, so screen-space fetches are not half-pixel corrected for D3D9; (3) the translated vertex programs read the PS3 vertex encodings (for example `advert_ln` normals are used as stored, where the PC program decodes `v * 2 - 1`). Of the PS3 element types only SHHD_3N fetches differently on D3D9 (RSX CMP: signed 11:11:10 normalised, w = 1; `display2/source/context/GCMContextSPU.cpp:1035-1048` against `display/include/display/device/d3d9/D3D9DeviceTypes.h:731-790`); for a PS3 source the model and level converter therefore writes every SHHD_3N element as F16_4 (x/1023, y/1023, z/511, 1), so D3D9 fetches what the RSX fetched and the translated programs need no decode. Other types fetch alike on both (F32 F/FLOAT, U8_4 UB256/UBYTE4, U8_4N UB/UBYTE4N, F16 SF/FLOAT16, S16 S32K/SHORT); S16_2N (S1/SHORT2N) and Colour (UB/D3DCOLOR) differ but do not occur. Vertex attribute semantics: the PS3 engine binds a declaration element to RSX attribute slot usage + index (`display2/include/display2/context/GCMFunctions.inl:911-959`, GCM usages `GCMContextSPU.h:480-493`: 0 POSITION, 1 BLENDWEIGHT, 2 NORMAL, 3 COLOR, 5 FOG, 6 PSIZE, 7 BLENDINDICES, 8 TEXCOORD, 14 TANGENT, 15 BINORMAL); the translator inverts it (slot 8 + n = TEXCOORDn). Every one of the 16,071 attribute reads of the translated vertex programs maps back to an entry of its effect's vertex input declaration (POSITION 0, NORMAL 0, TEXCOORD 0-5, TANGENT 0, BINORMAL 0, COLOR 0; the 288 vehicle effects read their position and normal as TANGENT/BINORMAL from stream 3); (4) PS3 vehicles have no vertex-texture damage and no `*NoDamage` techniques.
- *Fixed 2026-09-25, trees missing in the PS3 showroom:* the translated programs declared the whole constant file (`float4 C[256]` / `C[224]`). For a program with relative addressing fxc keeps the whole array and places the program's literals (`def`) after it, at c256 and up, past the 256 vertex constants of shader model 3, so the device could not create the shader: all 591 such vertex program instances (124 effects: every skinned `cs_*_skin`, `default_skin*` and SpeedTree/foliage program using `g_mWind`) were unusable, which removed the SpeedTree trunks and canopies. Checked: the SpeedTree/foliage programs' math, bindings (`g_mWind` c44-c59, `g_mLeaf` c60-c75) and input semantics against the retail PC bytecode match; the attribute map round-trips for every declaration (above). #### Console sources: lighting prepass, constant registers, flare miscompile (2026-09-25)

- **What each platform writes.** The effects' prepass output layout is chosen per platform (`amax/game/Shaders/Core.h:104-109`).
  - Consoles use `ENABLE_PREPASS_VIEWDEPTH`: one target holding normal.xy x 0.5 + 0.5 and linear view depth (depth / `g_vNearFar.w`) packed in z/w as floor(d x 255) / 255 and frac(d x 255) (`Common/Pixel.h:63-72`, `Common/Vertex.h:43-48`).
  - PC uses `ENABLE_PREPASS_DEPTHTEXTURE`: normal.xyz x 0.5 + 0.5 and alpha in target 0, post-projection z/w in target 1.
  - The bytecode matches: the recompiled 360 prepass programs (`road_ln`, `default_ln`) write only `oC0`, with depth in `.zw`; retail PC `road_ln` writes `oC0.xyz` and `oC1`. The PS3 prepass vertex programs bind `g_vNearFar` as the 360 ones do; the PC ones do not.
- **Targets and light passes** (`Graphics/Lighting/Prepass.cpp`).
  - Consoles allocate one A8R8G8B8 target (depth D24FS8). They light with `C_PointLights` / `C_SpotLights` (`psPointLights`, `psSpotLight*`: `UnpackViewSpaceNormal16` / `UnpackViewSpaceDepth16`, `deferred/shaders/psCommon.h:20-75`).
  - PC adds an R32F target 1 and lights with `Deferred::C_DynamicLights` / `C_Light` (`psDynamicLightsPrePass`: normal from target 0 `.rgb`, position from the R32F z/w).
  - A console source on PC therefore lit with the normal's z taken from the packed depth byte and positions from a target the console programs never write. This was a real fault, but not the cause of the near-white showroom ground (below).
  - The material pass reads the light buffer the same way on every platform (`Common/Lighting.h:119-133`, `.rgb`).
- **Change** (Blur1Multi overlays of `amax/game/Graphics/Lighting/Prepass.cpp` and `amax/game/Game/GameWorld/View/Main.cpp`; selected by `GameSource::IsConsole()`; PC sources unchanged).
  - Console sources get the console path:
    - one colour target (D24S8 depth, as the PC has no D24FS8);
    - `C_PointLights` and `C_SpotLights`, which the PC exe already compiles with all their shader variants, kept in the overlay keyed by the prepass so `Prepass.h` stays the base file;
    - tessellation width / 160 x height / 160 and the far clip, as on the consoles;
    - `RenderLights1`'s console sequence: clear, `MaskBefore` when enabled, mask, point lights, spotlights.
  - The 360 sequence (mask ends after the point lights, then a stencil clear) is used for 360 sources. The PS3's GPU sequence (mask ends after the spotlights) is used for PS3 sources; the PS3 takes that path itself when split-screen or with `g_debugLightSPU` off. Each console's defaults of `g_debugLightMaskBefore` (360: true) and `g_debugLightScreenSizeStencilThreshold` (PS3: 8.0) are applied.
  - `SpotLights.cpp` needs no change: its `PLATFORM_XENON` blocks are hierarchical-stencil render states and a null pixel shader for the stencil cones (:344-600), and the PC branch carries the same logic.
  - The console prepass render-pass list is used (Solid, Punch, DynamicObjectSolid, AnimatedObjectSolid; `Main.cpp:210-213`), and vehicles and ghosts are not scheduled into it (retail PC does so at detail 4 and in the UI). The PS3 has no `MaterialPrepass` technique for 304 vehicle effects, and FX then falls back to their colour technique (`FxContext.cpp:176-182`), which wrote car colour into the G-buffer under the showroom car.
- **Blob and drop shadow depth for console sources (bridged 2026-09-25).**
  - The console builds give blob shadows (`psScreenBlobShadows`) and drop shadows (`psDropShadowsViewNormal`) the hardware depth buffer as a texture: `Render::g_DepthStencilBuffer` has the back buffer's depth format (`render/source/utils/Globals.cpp:89-99`). The PS3 overrides it with the shared render buffer's depth (:63-69) and decodes D24 from RGBA8 bytes (`SampleDepthBuffer`, `render/shaders/psCommon.h:28-37`); the 360 reads the resolved depth.
  - The PC exe has no way to sample a D3D9 depth buffer. For PC sources `Main.cpp:1148-1165` copies the PC prepass's R32F z/w into that global buffer. Console sources have no such target, so the copy was skipped and those shadows read an unwritten buffer (no car shadows on either console source).
  - Bridge (`Blur1Multi/code/amax/game/Game/GameWorld/View/ConsoleDepth.{h,cpp}`, called from the `Main.cpp` overlay in the same copy block): a full-screen pass reads the console prepass target, unpacks view depth w = (z + w_byte / 255) x `g_MainPrepassDrawDistance` (the value the prepass bound as `g_vNearFar.w`), and writes clip z / clip w = a + b / w into the global buffer. a and b come from the view's own camera-to-device matrix (row-vector, clip = v x M): w and z are both linear in the camera depth coordinate, found as the row with the largest |M[k][3]|, so a = M[k][2] / M[k][3], b = M[3][2] - M[k][2] x M[3][3] / M[k][3]. Pixels the prepass left at its 0xFFFFFFFF clear get 1.0.
  - No console build does this: it is a bridge between the console prepass layout and the PC depth readers, exact up to the prepass's 16-bit packing (1/65536 of the draw distance). An INTZ depth texture would give the hardware depth the consoles sampled, but needs the whole depth path moved to INTZ.
  - Verified by screenshots only (race_long, first career event): the PS3 and 360 sources show a car shadow under and beside the player car (`Blur1Multi/_work/verify/shadows2/`, `x360_shadows/`); PC data unchanged (`pc_shadows/`). The depth values themselves were not compared against a PC-data frame.
- **Open: the PS3 SPU point-light default.** With one view and `g_debugLightSPU` on, the PS3 lights points on the SPU (`Prepass.cpp` `RenderLights2`, `JobQueuePrepassWorker.cpp`).
  - Its per-pixel formula is the GPU one: (1 - saturate(d² x falloff)) x saturate(N.L) x colour.
  - It quantises each channel to 8 bits with a +0x80 rounding term (:1085-1133).
  - It also writes a depth/height fog term per pixel into the lighting buffer (`fog` at :163, from `AddFog` in `RenderLights2`), into a byte of the output word. The GPU fallback writes alpha 1.
  - The PS3 material programs read only `.xyz` of the light buffer (854 of 854 `g_tDynamicLights` fetches in the translated programs), so if the fog byte is alpha it has no visible effect on them. Which channel it occupies, and whether another reader (crowd flags) uses it, is unverified.
- **The white showroom ground (fixed; apitrace of PS3, 360 and PC data at the same moment, `Blur1Multi/_work/run/trace_{ps3,x360,pc}.ps1`).** Draw by draw, the ground (RoadTwoSpec/Road effects) diverged where it samples `BlurScreenReflectionSampler`, the mirrored-scene reflection target. That target was already wrong: in its pass, the light-flare draws (`LightFlare_LN`, `SoftLightFlare_LN`) painted large full-bright areas. Two causes, one per console:
  - PS3: the effect converter placed parameters that sce-cgc left without a register (at c465-c467) on the lowest free D3D9 registers; `g_fLightFlareDepthBias` landed on c8, where the engine's view setup keeps `g_mView` (uploaded once per view outside FX, so FX's shared-binding conflict tracking does not cover it). Every later draw read a broken view matrix. `Ps3EffectConvert.cpp` now allocates top-down below c248 / c216 (8 registers of headroom for fxc's literal definitions): over the 820 effects no allocated vertex register meets any explicit binding register (explicit use ends at c191; allocations c234-c247); pixel allocations c206-c215 overlap only FX-shared parameters (`g_vRenderSettings` c206, `g_vRenderColour` c207), which FX re-uploads on conflict (`FxContext.cpp` `BindSharedParameters`).
  - Both consoles: d3dcompiler_47 compiles `1 - dot(abs(h), abs(h))` written with `dot()` into `dp2add r0, r0_abs, -r0, 1`, dropping one abs modifier, so every flare is full-bright where h.x or h.y is negative. RSX DP2 (`RsxTranslate.cpp` `Dot2`) and Xenos DP2ADD (XenosRecomp D3D9 mode, `dp2add_xenos` in `shader_common_d3d9.h`) now go through a multiply-and-add helper; a disassembly scan of all 7,574 PS3 and 6,718 360 programs finds no abs-modified `dp2add`.
  - Shader cache tags bumped (`rsx-hlsl-d3d9 3`, `xenosrecomp-d3d9 3`; the 360 tag moved again for the vertex fetch change in "Xbox 360 sources: SHHD_3N and the damage volume"). Result: both consoles show the dark wet cobbles of retail PC (`Blur1Multi/_work/verify/regfix/`); the PS3 race still runs.
- **Open:** in the showroom the PS3 source runs at about 6 ms GPU, the 360 source and PC data at about 30 ms; the difference is not explained.

#### Xbox 360 sources: SHHD_3N and the damage volume (2026-09-25)

360 car bodies were invisible in the showroom and in races (rims, lights and glass drew). Two faults, both in how 360 vehicle programs read their inputs:
- **SHHD_3N fetches.** XenosRecomp's D3D9 mode decoded SHHD_3N (Xenos 10_11_11, fetch formats 16/17) from the U8_4N the converter wrote, as `v * 2 - 1`. That rule never fired: Direct3D on the 360 patches each vfetch's format from the bound vertex declaration at draw time, so the compiled microcode carries format 0 in every fetch of the 820 retail effects. Every 360 program read SHHD_3N elements as [0, 1] values; vehicle morph offsets (TEXCOORD2/3) are SHHD_3N, so bodies were displaced. The converter now writes SHHD_3N as F16_4 (x/1023, y/1023, z/511, 1) for 360 sources too (`SceneTranscode.cpp` `ExpandsShhd`), which is what the Xenos signed-normalised fetch returned, and XenosRecomp passes every fetched element through unchanged (`shader_recompiler.cpp`, vertex fetch). The PS3 derivation and checks above apply unchanged.
- **Damage volume format.** Retail PC vehicle shaders were built with `_DAMAGE_USE_F32` and add the sampled volume straight to the position, so Blur1PC creates the volume A32B32G32R32F (`damage/DamageLayer.cpp`, `BLUR2PC_DAMAGE_VOLUME_F32`). The 360 programs decode the 8-bit encoding: the recompiled vertex programs compute v x 4 - 1.99216 (4 x 127/255; 127 = no damage). A zero-filled F32 volume read that way moved every body about 2 m off its wheels. The `DamageLayer.cpp` overlay creates and fills the volume as A8R8G8B8 for 360 sources, as the Xenon build did (`DamageVolumeF32()`); PS3 programs do not sample it.
- Shader cache tag `xenosrecomp-d3d9 3`. Verified: `x360shader-verify` 820/820; 360 race (race_long) draws the player's Focus and the AI cars (`Blur1Multi/_work/verify/x360_race/`, `x360_shadows/`).
- **Open:** FX's default binding for an unbound vehicle volume is a zeroed F32 1x1x1 dummy, which a 360 program would read as -1.99. No 360 car in the traced frames drew with the dummy bound.

Paths below are relative to `Blur1PC/code/mercury/library/` unless given in full. Converter: `Blur1Multi/code/mercury/library/util/x360convert/source/Ps3Texture.{h,cpp}`, reached through `ConvertTexturePayload`, `ConvertTextureLodHeader` and `ConvertTextureLodData` (`TextureConvert.cpp`) and `ConvertBundle` (`BundleConvert.cpp`) when `GetSource() == E_Source_PS3`.

**Serialised form.** `NglPs3Tex::SerialOutTexture` (`graphics/texture_export/source/targets/ps3tex.cpp:859-1022`) writes the `CellGcmTexture` fields one by one, big-endian (`ps3tex.cpp:845-850`; struct at `texture_export/source/targets/ps3/cell/gcm.h:512-528`):

| off | type | field |
|---|---|---|
| 0x00 | U16 | width |
| 0x02 | U16 | height |
| 0x04 | U8 | mipmap (level count) |
| 0x05 | U8 | format: `CELL_GCM_TEXTURE_*` (`gcm.h:120-149`), plus `LN` 0x20 for linear |

| 0x07 | U8 | cubemap |

|---|---|---|

| 0x88 | 0xAAE4 | DXT5 |

**Image layout** (`ps3tex.cpp:955-1008`):
- **DXT:** never swizzled and never byte-swapped. The blocks are the PC bytes. Power-of-two DXT is packed tightly with pitch 0. NPOT DXT is marked LN (0xA6 in the data) and uses the pitch of its top level.
- **Other formats without LN:** swizzled with `GCMSwizzleSurface` (`ps3tex.cpp:387-431`). The order is Morton: offset bit 2b is x bit b, bit 2b+1 is y bit b. It applies inside a min(w,h) square; a non-square level is a run of squares along its longer side, and texels over 32 bits are swizzled as 32-bit units.
- **LN formats:** rows at the top level's pitch at every level (`ps3tex.cpp:996-999`).
- **Texel byte order:** after layout, texels are stored big-endian per `GCMEndianSwapSurface` (`ps3tex.cpp:298-385`): 16-bit formats per U16, A8R8G8B8 per U32, float formats per component, B8 and DXT untouched.
- **Mip dimensions:** `max(1,(n+1)/2)`, counted in 4x4 blocks for DXT.
- **Cube maps:** face-major, each face ending on a 128-byte boundary (`ps3tex.cpp:1005-1007`).
- **Volume textures:** the exporter does not write them (`ps3tex.cpp:874-878`).

**PC side.** The PC side is `TextureDesc` plus levels (`D3D9TextureLoad.cpp:83-122`). Each level is read at `D3D9Texture2DSize` (`display/include/display/device/d3d9/D3D9DeviceTypes.h:590-667`), which rounds it up to 4 bytes; the PC exporter writes the same size (`texture_export/source/targets/pctex.cpp:105-116`). The pad bytes and `TextureDesc.Usage` in retail PC files are uninitialised writer output; the converter writes zeros.

**Bundles (`.bpr`).** Platform byte 4 (`E_Platform_PS3_LibGCM`). The PS3 bundler options (`tools/ResourceBundler/source/Bundler.cpp:276-282`) are: texels not swapped, not tiled, and resources aligned to 128. Level sizes are `floor(w/blockW)*floor(h/blockW)*bytesPerBlock` (`ProcessedMipmapChain.cpp:139-143`), so DXT levels under 4 texels take 0 bytes on PS3 and PC alike. L8 and A8R8G8B8 rows use the top level's pitch (`ExportArrayOfTextures2DGeneric.cpp:44-53, 183-208`; runtime `ResourceBundleSingle.cpp:201-212`). PC keeps the same levels without the row padding, back to back. Trailing zero bytes after the data (PC 16 to 1870, PS3 640 to 1920) are not read by `ResourceBundleReaderImpl3`.

The exporter's mip sizes `(n+1)/2` and the PC loader's `n>>1` differ for NPOT chains; the converter refuses such a level (the PC exporter does not mip NPOT textures, `pctex.cpp:285-290`).

#### Console audio: banks and audio objects

Retail Blur 1, PS3 and Xbox 360 against retail PC (extracts under `Blur1Multi/_work/extract/`). Audio source paths are relative to `Blur1PC/code/mercury/library/audio/source/`.

**Audio banks (`.baf`, tag `BANK`).** All three platforms use the same container, `BANK` version 4 (`common/WaveBank.h`, read by `common/WaveBankReader.cpp`):

- Layout: a 0x34-byte bank header, then one `WAVE` chunk per wave, then one `DATA` chunk per wave in the same order. Each `WAVE` chunk is a 60-byte base header plus a format-specific extra header.
- Byte order: PS3 and 360 write it big-endian (`chEndian` = 1). The game reader never swaps; `NON_NATIVE_BANK_READING_SUPPORT` is defined only in the BankInfo tools, and its extra-header swaps do not match the retail files.
- Data placement: in-memory banks pack the `DATA` chunks back to back. Streaming banks start every payload on a 2 KB boundary; each `DATA` header sits at `uDataStart - 8` behind zero padding.
- Formats (`common/SampleTypes.h`): PC and PS3 use 7 (4-bit ADPCM, 16-byte extra header) plus four PCM S16 waves (format 3, 20 bytes). The 360 uses 8 (XMA, 32 bytes) and 9 (XMA2, 32 bytes plus a big-endian seek table) plus the same PCM S16 waves.
- ADPCM codec (`core/decoderadpcm4bit.cpp` `DecodeBlock`): VAG-style, 33-byte blocks of 64 samples, stereo as an L block then an R block. It is read byte by byte, so the payload has no byte order. PS3 (SPU) runs the same scalar decode as PC; `DecodeBlock3` returns before its SPU vector body.
- Header swaps: in the PS3 ADPCM extra header only `uSize`, `uSampleRate` and `uNrSamples` are big-endian; the four U8 fields are untouched. PCM S16 samples are big-endian on PS3. PS3 and 360 never read them (`m_bTempAmaxNullFileReadHack`, `WaveBankManager.cpp` ~568); PC does.
- Mounting: PS3 `root_streaming.pak` stores `audio/<bank>` and is mounted at `/` (`amax/game/GameSystems.cpp`, `PLATFORM_PS3`). PC stores the banks at the pak root and mounts at `/audio/`. PS3 `boot_rampak.pak` audio is a byte copy of the same files in `root.pak`.

PS3 against PC, 192 shared banks and 2,690 waves:

- All 265 `root_streaming` waves and the 19 waves of the four `root` music banks are byte-identical.
- Every wave in the other 121 `root` banks was re-encoded at a lower rate with the same duration: 1,592 at 48→36 kHz, 680 at 36→24 kHz, 134 at 48→24 kHz.
- All other header fields match on every wave.
- `menumusic.baf` and `menumusic_ns.baf` store their waves in a different order. Waves are looked up by name (`WaveBankManager.cpp` 253/449/823), so the order has no effect.
- PS3 flags 35 more `root_streaming` banks as streaming (54 against PC's 19). Their payload is identical; PC keeps them in memory.

Xbox 360 banks and their PC conversion (T075, D15; `XmaBankConvert.cpp`, `AudioCacheFs.cpp`):

- Versions: retail and Aug 31 banks are `BANK` v4; the Nov prototypes write v5, which inserts one U32 after the 60-byte base header of XMA and PCM rows (meaning unknown; Blur2Test `extract_xbox_baf_audio.py`), not of ADPCM rows (76 bytes as in v4), and puts `CUE ` chunks between the rows. Nothing on PC reads `CUE `.
- XMA rows: `XMAWave` (rate, bits, channels, stride, loop start and end in bits, U8 loop count, U8 subframe data, frame count); format 9 follows it with a seek table of frame-count U32s. Data is XMA2 in 2 KB packets, each opening with a 32-bit header, so a loop start of bit 32 is the first frame.
- PC rows, from the retail PC banks: ADPCM `uSize` 0, `uNrInterleavedStreams` 0, `uBitsPerSample` 4, `uLoop` 0/1, `uNrSamples` = the sample frames of the source; data = ceil(frames/64) 33-byte blocks per channel with no prefix. Level and flags (0x19) are the same values as the 360 rows. Every `DATA` chunk's size counts its own 8-byte header (payload + 8); a bank whose sizes omit it fails in `WaveBankReader` ("Unknown chunk tag", "Trying to skip chunk of size 0").
- The PC audio memory budget is sized for ADPCM banks. Decoded 16-bit PCM (about 4× larger) runs it out of memory on the first sound banks (`AssertOutOfMemory`), so XMA is re-encoded to ADPCM with WaveBundler's own encoder (`tools/Audio/WaveBundler/Library/fmt_adpcm.cpp` `PcmToAdpcm`, `tools/Audio/LeeADPCM/adpcm64.cpp`). Retail X360 `pickups.baf` converts to 2,414,962 bytes; retail PC's is 2,414,995.
- Lengths: FFmpeg's XMA2 decoder applies the end trim, and its lengths equal the retail PC `uNrSamples` for 121 of 124 `car_collisions` waves and 54 of 68 `pickups` waves; every other one is a looping wave, off by 1 to 224 samples (cause not established). One 360 row, `MOD_ShieldActivate` in `pickups.baf`, is 48,014 Hz; it is kept as stored. Blur2Test's vgmstream output pads to whole 512-sample frames (up to 512 samples longer); the samples themselves are identical (Nov 9 `Pickups`, 68 of 68).
- Round-trip quality against the vgmstream decode (`xma_verify --ref --pc`): mean SNR 17.7 dB on `car_collisions` and 27.2 dB on Nov 9 `Pickups`. Retail PC's own ADPCM for the same waves, measured against the same XMA decode, gives 14.9 and 15.9 dB (it was encoded from the source, not from the XMA).

`BafConvert.cpp` (PS3 only) swaps the headers and the PCM samples and keeps the PS3 layout. 34 of 192 banks come out byte-identical to PC. Repacking the 35 streaming banks into PC's in-memory layout would give 69; the converter does not repack. The remaining banks differ only by the PS3 re-encode and wave order. Two points are untested: how the 24 kHz ADPCM sounds on the PC mixer (retail PC only plays 36 and 48 kHz), and the stream count with 54 streaming banks.

**Audio objects (`audio/dat/*.dat`, tag `AOBJ`).**

- Reader: `Definition.cpp:73-128`, and the component walk `Object.cpp:449-1120` (`CalculateComponentFootprint`).
- Writer: `Blur1PC/code/mercury/tools/Audio/XMLtoDat/audioDatafile.cpp:720-800`.
- Header: six U32s. The tag is read as the U32 0x414f424a, so PC files begin with "JBOA". Then version 2.11 (`include/Audio.h:61`), string-table offset, name offset, component count and frame skip.
- Components: each is a U32 type (`components/Component.h` enum `Types`) followed by its `Data` struct. The walk advances by `<Class>::DataSize`: `sizeof(Data)`, plus trailing arrays for 33 classes. Those arrays are effect lists (U32), mixer `InputGain` rows, `Array`/`Selector`/`Sequence` elements, function points, state items, sound-table waves and script words. Their counts are U16 `ArraySize` members, and effects come before inputs or waves (`MonoToMonoMixer.cpp:25`, `MonoOneShotSoundTable.cpp:33`).
- Field types (`Component.h:62-68`): `StrOffset`, `AudioFloat` and `AudioInt` are 32-bit; `ArraySize`, `Com`, `Out` and `Msg` are 16-bit; `Control`/`Event` = two 16-bit fields; `Option` = `Control` + F32.
- Exporter byte order: header, type words, effect lists and script bodies are written as swapped U32s (`CommandLineApp.h` `WriteBytes`). Data members go through per-width convertors (`XMLtoDat/DataTypeConversion.cpp`). So each field is swapped at its own width. A flat 4-byte swap matches none of the 365 files, and a script body is a plain stream of U32 words.
- Mixer flags: `MixerComponent::Flags` (`Component.h:728`, a U32 bitfield) holds `10 00 00 00` in every console mixer (225) and every PC mixer (337). The reader uses only `nSurroundMode`, which is 0 from those bytes under both bitfield layouts. How any other value maps is unknown.
- Padding: struct padding holds leftover exporter memory, often string fragments. It differs between builds and nothing reads it.
- Types in use: 85 component types on the consoles, 87 on PC (PC adds `StereoSend` and `StereoReturn`).
- Files: PS3 and 360 ship 371 files each, byte-identical except `finalperksubmix.dat`. PC ships 365; the six extra console files are `collisioncar3dmixer`, `collisionscrape3dmixer`, `collisionworld3dmixer`, `do_concrete_fence_chain`, `do_vehicle_alarm` and `po_metalalloyrim`.

`AobjConvert.cpp` swaps every field at its reader width, from a table generated from the headers:

- The table has 111 component classes, each line citing its `Data` struct and `DataSize`. Its layouts walk every retail PC, PS3 and 360 file exactly to its string table.
- The mixer flags word is copied, and any value other than `10 00 00 00` fails the file.
- Struct padding and the string table are copied.
- An unknown type fails the whole file, as does `eSurroundDelay`, which has no data size in `Object.cpp:1015`. So does any component that runs past the string table, or a walk that does not end exactly on it.

### Timing (frame-rate coupling)
Confirmed against https://github.com/Aib0t/write-ups/blob/main/blur-fps-unlock/readme.md:
